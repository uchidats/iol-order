## 記録のルール

- 優先順位は、今回指定された「直近」「今後」と列挙順を基にした初期案。P0は直近、P1は次段階、P2はその後。同じ区分では番号順を目安とし、着手順の最終決定はユーザーが行う。期限は未設定。
- 進捗は「未着手・設計中・実装中・実装済み・保留」などで記録し、テストと本番公開は別の欄で管理する。テストコードの存在、commit、pushだけで「テスト済み」「本番公開済み」としない。
- 「テスト済み」は対象範囲・結果・根拠を記録する。過去の作業報告を参照した場合は、その旨を明記し、今回再実行した結果と区別する。
- 「本番公開済み」は画面と必要なサーバー処理の反映を確認して記録する。本番での実操作を確認していなければ、その状態も残す。
- 担当AIは、実績または明示的な割り当てが確認できる場合だけ記載する。「原稿作成」と「組み込み担当」は別。未定のものを、並行作業中のAIへ自動で割り当てない。
- 更新時は確認日、変更内容、根拠、残作業を併せて更新する。採否・範囲・優先順位・担当の最終決定はユーザーが行う。

### R01 施設の事前登録の確認結果

- **実装**: [facility-preregistration.md](facility-preregistration.md)、[サーバー処理](../functions/src/facility-preregistrations.js)、[画面](../src/ui/facility-preregistrations.js)、[参加処理](../functions/src/members.js)を確認。本体commitは `50253a5`、mainへの取り込みは `88ccbee`。
- **機能範囲**: platformAdminのみが事前登録・一覧・編集・取り消しを実行できる。承諾前は施設が未有効で、初期管理者の所属はまだ作らない。指定メールアドレスの確認済み利用者が期限内に承諾すると、施設の有効化と管理者所属の作成を同一トランザクションで行う。初期管理者への案内メールは送信しない。
- **テスト**: [2026年10月27日の作業報告](CLAUDE_REPORT.md)に、単体241件、Rules 61件、Functions 172件、Functions E2E 11件、ブラウザ121件の結果あり。ブラウザのWebKit手術日テスト1件は既知の不安定さがあり、再実行で成功したとの報告。これらは当該変更時の検証一式の件数で、本機能だけの件数ではない。今回は再実行していない。
- **本番反映**: 同報告に、新規4関数（`preregisterFacility`、`listFacilityPreregistrations`、`updateFacilityPreregistration`、`cancelFacilityPreregistration`）と既存2関数（`respondMembership`、`listMyPendingMemberships`）のデプロイ成功、画面のpush・反映確認の記録あり。Rulesは変更なし。今回は `node scripts/verify-deployed.mjs` を1回実行し、公開サイトのimport mapとCSS・main.jsのバージョンが手元と一致した。サーバーの稼働状況は今回は再照会していない。
- **残る確認**: 本番での実施設登録・参加承諾はユーザー確認待ち。今回も実施していない。施設が有効になっても、実際の注文受付対象への追加は別の運用判断であり、許可リストは変更していない。

### R02 承認・却下結果の申請者向けメール通知

現状の [facility-applications.md](facility-applications.md)、[申請・承認処理](../functions/src/facility-applications.js)、[トリガー定義](../functions/index.js)では、申請作成時に**運営者へ**知らせる通知はあるが、承認・却下結果を**申請者へ**送る処理はない。

次に決める内容は、承認・却下それぞれの文面、却下理由の扱い、送信時点、送信失敗時の確認・再送方法。申請者と初期管理者が異なる場合の通知先も決める。実装時は、審査結果の保存とメールの送信結果を分け、同時操作や再試行で同じ結果通知が重複しないこと、送信停止・テスト用宛先の設定が守られることを検証する。詳細仕様は未確定。

### R03 オンラインマニュアルの組み込み

使用する成果物は [docs/manual/README.md](manual/README.md) と、初めての利用者・注文者／代行入力者・副管理者・管理者向けの4原稿。作成AIはGemini。

次に決める内容は、メニューなどの入口、ページの表示方法、閲覧対象、原稿の更新方法。施設の事前登録など最新機能との整合を確認してから組み込む。組み込み後は、スマートフォン・PCでの表示、原稿間のリンク、注文画面への復帰を確認する。原稿が存在することを、サービス内で利用可能であることと同一視しない。

### R04 サービス紹介ページの組み込み

使用する成果物は [紹介原稿](introduction/service-introduction.md) と [編集用確認メモ](introduction/review-notes.md)。作成AIはCodex。確認メモは掲載本文に含めない。

当面の閲覧対象は**platformAdminのみ**。実装前に閲覧制限の方法を決め、メニューを隠すだけで限定公開できたと扱わない。直接URLなどからのアクセスも確認する。一般向け公開への変更はユーザーが決定する。

組み込み前には、施設名の掲載可否、利用対象、メール運用、未確定の提供条件を確認する。確認メモには作成時点の「施設事前登録は開発中」という記述が残っており、R01の最新状況との照合が必要。今回、原稿・確認メモは変更しない。
