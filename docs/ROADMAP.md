## 記録のルール

- 優先順位は、今回指定された「直近」「今後」と列挙順を基にした初期案。P0は直近、P1は次段階、P2はその後。同じ区分では番号順を目安とし、着手順の最終決定はユーザーが行う。期限は未設定。
- 進捗は「未着手・設計中・実装中・実装済み・保留」などで記録し、テストと本番公開は別の欄で管理する。テストコードの存在、commit、pushだけで「テスト済み」「本番公開済み」としない。
- 「テスト済み」は対象範囲・結果・根拠を記録する。過去の作業報告を参照した場合は、その旨を明記し、今回再実行した結果と区別する。
- 「本番公開済み」は画面と必要なサーバー処理の反映を確認して記録する。本番での実操作を確認していなければ、その状態も残す。
- 担当AIは、実績または明示的な割り当てが確認できる場合だけ記載する。「原稿作成」と「組み込み担当」は別。未定のものを、並行作業中のAIへ自動で割り当てない。
- 更新時は確認日、変更内容、根拠、残作業を併せて更新する。採否・範囲・優先順位・担当の最終決定はユーザーが行う。

### R19 注文の送信直後の取り消し(10秒)

- **確認日**: 2026-11-01(Claude Code)。ブランチ `feature/order-cancel-window`(main `299f747` から)。ユーザー指定: 猶予は10秒、ボタンは取消可能な間だけ表示して自動で消す、カウントダウン・残り秒数・プログレスバーは出さない、成功は「注文を取り消しました」、期限後・通信の遅れは取り消せなかったことを明確に表示、猶予とメールの保留はサーバーで保証。
- **サーバー**: `createOrder` が注文を即時に保存し、`cancelUntilMs` = 受付時刻 + 10秒(`ORDER_CANCEL.windowMs`)を注文に、同じ時刻を `sendAfterMs` としてメール(ディーラー宛て・注文控え)に記録。期限とサーバーの現在時刻を返す。`processMail` は `sendAfterMs` の前は送らず、`sendOrderMail` は時刻まで待ってから送る(止まっても10分ごとの処理が送る)。新しい `cancelOrder`(注文した本人・所属あり・期限より前・全メールが未確保)で、メールを `cancelled`、注文を `cancelled: true`・`status: cancelled` にする(操作の記録 `order.cancel`)。送信の確保と取り消しはトランザクションで排他。`syncOrder` は取消済みの状態を上書きしない。ディーラーの受信の索引は期限 + 2秒の後に作り、取り消した注文は作らない(万一の既存の索引には印を付け、一覧・週表示・詳細に出さない)。
- **画面**: 完了画面に「取り消す」を、サーバーの期限と現在時刻の差だけ表示(端末の時計は使わない)。押した後は結果が出るまで消さない。成功: 題名「注文を取り消しました」・状態「取消済み」。期限後(サーバーが拒否): 「取り消せませんでした。取り消せる時間を過ぎたため、注文は受け付けられ、ディーラーへ送信されます。」。通信の失敗: 「取り消せたか確認できませんでした…注文履歴で…」。再送の受付済み・期限のない応答には出さない。注文履歴は「取消済み（ディーラーへは送信していません）」で一覧に残す。過去の注文との重複の確認からは、状態 `cancelled` のため従来どおり外れる。マニュアル 02 に追記。
- **影響**: 既存の注文・メール(`sendAfterMs` なし)は従来どおり即時。注文番号は戻さない(欠番)。メールは約10秒遅れて送られる。
- **論理削除した注文のディーラー画面での扱い(公開前にあわせて修正)**: 論理削除は施設の履歴の整理で、取り消しではない。その発注先へ注文メールを送った(accepted)注文は、削除後もディーラー画面に出す(取り消されたように見せない)。送っていない(削除で送信を中止・失敗・未送信)注文は、一覧・週表示・詳細に出さない(届いていない注文を画面だけで手配させない)。判定は `deletedAndNotSent` に1つにまとめ、削除の処理が受信の索引に `deletedUnsent` の印を付け、索引の作成はトランザクションの中で注文を読み直す(削除・取り消しと同時でも漏れない)。マニュアル 03 の「11. 注文履歴から注文を削除する」に追記。
- **取り消し後の再注文(2026-11-01、ブランチ `feature/order-cancel-restore`)**: サーバーが取り消しを確定したときだけ、完了画面を閉じ、送信時の入力内容(全明細のモデル・トーリック/多焦点・度数・枚数・手術日・担当医・発注先と備考。下書きの復元と同じ `lensLines.snapshot()/restore()`)のまま注文入力画面へ戻し、「注文を取り消しました。内容を修正して、もう一度送信できます」と表示。戻した内容は下書きにも保存。再送は通常の確認画面・重複警告を通り、入力の確認のたびに新しい requestId を作るため新しい受付番号になる(取消済みの元注文は履歴に残る。過去の注文との重複確認からは従来どおり外れる)。取り消せなかったとき(期限後・通信の失敗)は完了画面のまま戻さない。取り消さずに「新しい注文を入力する」は従来どおり新規入力。「取り消す」と10秒の猶予・サーバーは変更なし。マニュアル 02 を更新。テスト: ブラウザ(複数レンズの復元と一部の修正・新しい受付番号での再注文・元の注文の取消済み・取り消せないときに戻さない・新規入力、3ブラウザ。既存の完了画面の取り消しの確認を新しい動作に更新)、注文の再送・下書き・重複警告・注文履歴・マニュアル、unit。未 push
