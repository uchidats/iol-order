# ディーラー専用画面の Microsoft ログイン(設定手順と安全上の扱い)

**状態: 実装・自動テストまで(ブランチ `fix/dealer-ms01-device-proof`。Codex のレビュー `dealer-microsoft-login-audit.md` の MS-01〜MS-03 と、統合版の最終レビュー `dealer-auth-integrated-final-audit.md` の MS-01 の残り(連携の解除の経路)に対応)。本番の Microsoft Entra のアプリ登録・Firebase の設定・機能の有効化は未実施で、ユーザーの承認後に行う。** 本書にはシークレット(クライアント シークレットの値など)を書かない。

## 何ができるか
- ディーラー専用画面(`dealer.html`)のログイン画面に「Googleでログイン」「Microsoftでログイン」を並べ、その下にメールのリンク(パスワード不要)を置く。医療機関の画面のログインは変更しない。
- Microsoft は Firebase Authentication 標準の `OAuthProvider("microsoft.com")`。企業(Microsoft Entra ID / Microsoft 365)と個人の Microsoft アカウントの両方を想定する(テナント `common`)。毎回アカウントの選択画面を出す(`prompt=select_account`)。
- スマートフォンでもポップアップを使う。リダイレクト方式は、認証の画面が別のドメイン(`medconf-iol-dev.firebaseapp.com`)になり、ブラウザの保存の分断(Safari・Chrome の第三者ストレージの制限)で失敗しやすいため使わない。ポップアップがブロックされた場合は、許可するかメールのリンクを使うよう案内する。

## 安全上の扱い(サーバーで確認する)
- **参加(招待の承諾)は、どのログイン方法でも、招待されたメールに届く確認コードで行う**(Google ログインと共通。G-02-R1)。Microsoft のセッションでもコードを受け取れば参加できるが、参加しただけでは Microsoft でのログインは使えない(下の登録が必要)。
- **Microsoft アカウントが連携された UID は、ログイン方法にかかわらず、本人が登録した Microsoft アカウントでなければ使えない(MS-01)。** トークンの `firebase.identities["microsoft.com"]` に、登録(`dealerStaffIndex/{uid}.trustedMicrosoftIds`)と一致しない ID があれば、Microsoft・メールのリンク・パスワード・Google のどれでログインしても、会社・一覧・詳細・会社の候補を拒否する(理由 `microsoft-unregistered` を返し、画面は登録の手順を出す)。未登録の Microsoft のセッションからパスワードを設定して入り直す経路(Codex の再現)も拒否する。
  - Microsoft アカウントのメールは組織の管理者が変更できる場合があり、確認済みとは限らない(nOAuth の問題)。メールの一致・UID の一致・ログイン方法・`email_verified` は本人の証明にしない。
- **閲覧は確認済みの端末からだけ(MS-01 の連携の解除の経路。統合版の最終レビュー)。** 連携を外してパスワードで入り直したトークンは、トークンの情報(ログイン方法・連携中のプロバイダー・`email_verified`)だけでは本人と区別できない。そこで、会社・一覧・詳細・担当施設・会社の候補は、メールの確認コードで確認した端末からだけ受け付ける(詳細は [dealer-portal.md](dealer-portal.md) の「確認済みの端末」)。連携の解除・再連携・ログイン方法の変更では、サーバーの記録は消えない。最初の API の前に連携を外した場合も同じ。
  - 心当たりのない Microsoft が連携されていたときは、登録せずに「連携を解除する」で外せる(外した後も、閲覧には確認済みの端末が要る)。
- **登録は、承認済みのメールに届く確認コードで行う(MS-03)。** 手順: 受注一覧の「Microsoftアカウントを連携」→ 連携(`linkWithPopup`。連携済みなら省略)→ トークンを更新 → `sendMicrosoftCode`(承認済みのメールにコード)→ `trustMicrosoft`(コード)。連携の直後のトークンは `microsoft.com` になるが、登録はログイン方法を問わないので、そのまま登録できる。
  - コード: 8桁、ソルト付きハッシュ、10分・1回・誤り5回まで、送り直しは1分あけて24時間に5回まで。UID・メール・**そのとき連携されている Microsoft の ID** に結び付け、別の Microsoft の ID・別の UID には使えない。登録と同じトランザクションで消費する。
  - 連携の後に登録が終わらなかった場合(送信の失敗・画面を閉じたなど)は、次のログインで「Microsoftアカウントの登録」の画面になり、確認コードから再開できる(連携は省略)。登録が終わるまでは、どのログイン方法でも閲覧できない(会社・施設の情報は出さない)。
- **登録の条件(MS-02)**: いま有効な所属(担当者が有効・会社が有効・承認済みのメールがログインのメールと一致)があること。所属の記録(索引)だけでは認めない。確認はコードの送信と登録のトランザクションの中で行い、無効化・停止と競合した登録は確定しない。担当者を無効化すると、登録済みの Microsoft と送信中のコードを消す(有効に戻した後は、確認コードで登録し直す)。
- **連携・解除・再連携**: 1つの UID に登録できる Microsoft は1つ(登録し直すと置き換え)。別の Microsoft に連携し直すと、確認コードで登録し直すまで閲覧できない。同じ Microsoft を再連携した場合は、登録済みのまま使える。登録した Microsoft が別の UID に連携されても、その UID に有効な所属と登録がなければ何も見えない(所属は UID ごと。メールの一致で権限は移らない)。
- 既存の UID との自動的な統合、メールの一致だけによる権限の移行はしない。別の UID になった場合の移行は、Google ログインと同じ正式な手順(旧 UID の無効化 → 再招待 → 確認コードで承諾)。
- メール未確認(`email_verified` が true でない)のアカウント、未招待、他社の所属、無効化された担当者、機能の停止中は、Microsoft でも拒否する(Google・メールのリンクと同じ確認)。認証そのもの・Auth 側の連携の操作は停止スイッチでは止まらない(ログイン後に「現在ご利用いただけません」)。
- 確認コードのメールは注文メールと同じ送信の設定に従う。送信の停止中・テスト用の宛先だけへの送信中は、本人にコードが届かないため登録できない(安全側)。

## 本番で必要な設定(承認後に運営者が行う。今回は行っていない)
### 1. Microsoft Entra 管理センターでアプリを登録
1. Microsoft Entra 管理センター → アプリの登録 → 新規登録。
2. 名前: 例「IOL Order ディーラー画面」。
3. サポートされているアカウントの種類: **「任意の組織ディレクトリ内のアカウントと個人の Microsoft アカウント」**(企業と個人の両方)。企業だけにする場合は「任意の組織ディレクトリ内のアカウント」とし、Firebase 側のテナントの指定も合わせる。
4. リダイレクト URI(Web): **`https://medconf-iol-dev.firebaseapp.com/__/auth/handler`**(Firebase の認証ドメイン。Firebase Console の Microsoft の設定画面に表示される値と一致させる)。
5. 登録後、「アプリケーション (クライアント) ID」を控える。
6. 証明書とシークレット → 新しいクライアント シークレット。**値は Firebase Console にだけ入力し、リポジトリ・文書・チャットに残さない。** 有効期限を決め、期限前に更新する運用にする。
7. API のアクセス許可: 既定の Microsoft Graph `User.Read`(委任)で足りる。`openid`・`email`・`profile` を含める。管理者の同意が必要な組織では、各社の管理者の同意が要る場合がある。

### 2. Firebase Console(プロジェクト medconf-iol-dev)
1. Authentication → Sign-in method → **Microsoft を有効化**し、アプリケーション (クライアント) ID とクライアント シークレットを入力する。
2. 承認済みドメインに `iol.medconf.jp` があることを確認する(医療機関の画面と共通)。
3. ユーザー アカウントのリンクの設定を確認する(既定値と決め付けない)。この設定の変更は医療機関の画面にも及ぶ。
4. Microsoft を有効にすると、医療機関の画面の Firebase プロジェクトでも Microsoft の認証方式が有効になる(医療機関の画面にはボタンを出していない)。

### 3. 有効化の前の確認(承認された実アカウントで)
- Entra の企業アカウント・個人の Microsoft アカウントで: ポップアップの動作(PC・スマートフォン・Safari)、`email_verified` の値、既存の UID との関係(競合 `auth/account-exists-with-different-credential` になるか、同じ UID か、別の UID か)。
- 確認コードで参加 → 「Microsoftアカウントを連携」→ 確認コードで登録 → 次回 Microsoft でログインして閲覧できること。登録していない Microsoft アカウントでは、どのログイン方法でも閲覧できないこと。確認コードのメールが届くこと(迷惑メールの扱いを含む)。
- 実際の連携の直後のトークン(`sign_in_provider`)、連携済みで登録が未完了の状態からの再開、`auth/credential-already-in-use`・`auth/account-exists-with-different-credential` の表示。
- 実トークン・シークレットはログ・報告に残さない。

## スマートフォンのポップアップ(O-01、Low)
- 現行はスマートフォンでもポップアップ(`signInWithPopup`・`linkWithPopup`)を使う。認証ドメインが別(`medconf-iol-dev.firebaseapp.com`)で、リダイレクト方式は第三者ストレージの制限で失敗しやすいため(Firebase 公式の代替策の1つ)。コードの変更は今回は行わない。ポップアップは脆弱性ではなく、使い勝手とブロックの問題として実機で確かめる。
- 公開前に実機で確認すること: iPhone Safari・Android Chrome・PC で、(1) アカウントの選択、(2) 組織のポリシー・同意画面・MFA、(3) 別の画面(認証アプリ・メール)から戻ったときにポップアップが続くか、(4) キャンセル・ブロック時の案内とメールのリンクへの切り替え、(5) 連携(`linkWithPopup`)でも同じ動作か。今回の WebKit のブラウザテストは偽の SDK で、実 Microsoft のポップアップの試験ではない。
- 通常の利用を妨げる場合は、認証ドメインを同じドメインにする(`iol.medconf.jp` で `/__/auth/` を配信する)などのリダイレクト方式の対応を別途検討する。

## 既知の制限
- 本番の Firebase が Microsoft のメールを未確認(`email_verified: false`)として発行する場合、Microsoft でのログインは「メールアドレスの確認が済んだアカウントのみ利用できます」となり使えない(安全側)。その場合はメールのリンクを使う。実アカウントでの確認が必要。
- Microsoft の連携が別の UID に付いている(`auth/credential-already-in-use`)場合は、案内してコードを送らない。運営者が状況を確認する。
- 登録の解除の画面はない(同じ UID で別の Microsoft を登録し直すと置き換わる。担当者の無効化で登録も消える)。
- 第三者が Firebase のアカウント(UID)そのものを操作できる状態(例: 未登録の Microsoft が自動で既存の UID に結び付き、そのセッションで連携を外してパスワードを設定する)では、トークンだけでは本人と区別できない。この場合も、注文の情報は確認済みの端末(本人のメールの確認コードで確認した端末)からしか取得できない。ただし、第三者はその UID でパスワードの設定・ログイン方法の変更などの Firebase のアカウント操作はできる(本システムの範囲外。本人のアカウントの安全の問題)。本番の Firebase は通常、信頼できないプロバイダー(Microsoft)を同じメールの既存アカウントへ自動では結び付けない(競合)ため、実アカウントで「自動で結び付かない」ことを有効化の前に確認する(エミュレータは結び付ける)。
- 確認済みの端末の値は、ブラウザの保存領域(localStorage)にある。保存を消した・別のブラウザ・プライベートブラウズでは、確認コードで確認し直す。端末の値が盗まれた場合(端末の乗っ取り・画面の脆弱性)は、担当者の無効化で消せる。
