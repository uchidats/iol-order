# ディーラー専用画面の Microsoft ログイン(設定手順と安全上の扱い)

**状態: 実装・自動テストまで(ブランチ `feature/dealer-auth-bindings`。担当者 ID × 認証主体のホワイトリストへの作り直し。詳細は [dealer-portal.md](dealer-portal.md) の「ログインと本人確認」)。本番の Microsoft Entra のアプリ登録・Firebase の設定・機能の有効化は未実施で、ユーザーの承認後に行う。** 本書にはシークレット(クライアント シークレットの値など)を書かない。

## 何ができるか
- ディーラー専用画面(`dealer.html`)のログイン画面に「Googleでログイン」「Microsoftでログイン」を並べ、その下にメールのリンク(パスワード不要)を置く。医療機関の画面のログインは変更しない。
- Microsoft は Firebase Authentication 標準の `OAuthProvider("microsoft.com")`。企業(Microsoft Entra ID / Microsoft 365)と個人の Microsoft アカウントの両方を想定する(テナント `common`)。毎回アカウントの選択画面を出す(`prompt=select_account`)。
- スマートフォンでもポップアップを使う。リダイレクト方式は、認証の画面が別のドメイン(`medconf-iol-dev.firebaseapp.com`)になり、ブラウザの保存の分断(Safari・Chrome の第三者ストレージの制限)で失敗しやすいため使わない。ポップアップがブロックされた場合は、許可するかメールのリンクを使うよう案内する。

## 安全上の扱い(サーバーで確認する)
- Microsoft でのログインは、**確認コードで担当者に紐付けた Microsoft の固有ID**(トークンの `sign_in_provider` が `microsoft.com` のときの `identities["microsoft.com"]`。ちょうど1つ)と、**確認したブラウザ(端末の値)** の両方がそろうときだけ通す(更新したトークンの identities は、そのセッションで認証したアカウントと限らないため。AB-02)。メールの一致・UID・同じ UID に連携されたほかのプロバイダーは根拠にしない。
- 初回(参加を含む)は、ログインのメール(=承認済みのメール。サーバーが担当者・招待と照合して確定)に届く確認コードで紐付ける。Microsoft のトークンの `email_verified` が false でも、確認コードを証明にするので使える。メールが取れない・承認済みのメールと違う場合は拒否する(推測で補わない。個人アカウントなど別のメールは今回は使えない)。
- Microsoft アカウントのメールは組織の管理者が変更できる場合がある(nOAuth)。メールの一致だけでは本人としない。紐付けの後にメールが変わった場合は、承認済みのメールと一致しないので使えない(安全側)。
- Firebase のアカウントの連携・解除は使わない(「Microsoftアカウントを連携」の画面はない)。未登録の Microsoft が既存の UID に自動で結び付いても、パスワードを設定・連携を解除して入り直しても閲覧できない。
- 担当者の無効化で、Microsoft を含むすべての紐付けが一度に失効する(世代)。機能の停止中は拒否する。認証そのものは停止スイッチでは止まらない(ログイン後に「現在ご利用いただけません」)。
- 確認コードのメールは注文メールと同じ送信の設定に従う。送信の停止中・テスト用の宛先だけへの送信中は、本人にコードが届かないため使えない(安全側)。

## 本番で必要な設定(承認後に運営者が行う。今回は行っていない)
### 1. Microsoft Entra 管理センターでアプリを登録
1. Microsoft Entra 管理センター → アプリの登録 → 新規登録。
2. 名前: 例「IOL Order ディーラー画面」。
3. サポートされているアカウントの種類: **「任意の組織ディレクトリ内のアカウントと個人の Microsoft アカウント」**(企業と個人の両方)。企業だけにする場合は「任意の組織ディレクトリ内のアカウント」とし、Firebase 側のテナントの指定も合わせる。
4. リダイレクト URI(Web): **`https://medconf-iol-dev.firebaseapp.com/__/auth/handler`**(Firebase の認証ドメイン。Firebase Console の Microsoft の設定画面に表示される値と一致させる)。
5. 登録後、「アプリケーション (クライアント) ID」を控える。
6. 証明書とシークレット → 新しいクライアント シークレット。**値は Firebase Console にだけ入力し、リポジトリ・文書・チャットに残さない。** 有効期限を決め、期限前に更新する運用にする。
7. API のアクセス許可: 既定の Microsoft Graph `User.Read`(委任)で足りる。`openid`・`email`・`profile` を含める。管理者の同意が必要な組織では、各社の管理者の同意が要る場合がある。

### 2. Firebase Console(プロジェクト medconf-iol-dev)
1. Authentication → Sign-in method → **Microsoft を有効化**し、アプリケーション (クライアント) ID とクライアント シークレットを入力する。
2. 承認済みドメインに `iol.medconf.jp` があることを確認する(医療機関の画面と共通)。
3. ユーザー アカウントのリンクの設定を確認する(既定値と決め付けない)。この設定の変更は医療機関の画面にも及ぶ。
4. Microsoft を有効にすると、医療機関の画面の Firebase プロジェクトでも Microsoft の認証方式が有効になる(医療機関の画面にはボタンを出していない)。

### 3. 有効化の前の確認(承認された実アカウントで)
- Entra の企業アカウント・個人の Microsoft アカウントで: ポップアップの動作(PC・スマートフォン・Safari)、`email_verified` の値、既存の UID との関係(競合 `auth/account-exists-with-different-credential` になるか、同じ UID か、別の UID か)。
- 「Microsoftでログイン」→ 確認コードで紐付け(参加)→ 次回は別の端末でもコードなしで閲覧できること。紐付けていない Microsoft アカウントでは閲覧できないこと。確認コードのメールが届くこと(迷惑メールの扱いを含む)。
- Microsoft の固有ID(Firebase が確定する値)が、企業(Entra)・個人・ゲストのどれでも毎回同じであること。トークンにメールが入ること。同じメールの既存アカウントと自動で結び付かないこと(競合 `auth/account-exists-with-different-credential` の表示を含む)。
- 実トークン・シークレットはログ・報告に残さない。

## スマートフォンのポップアップ(O-01、Low)
- 現行はスマートフォンでもポップアップ(`signInWithPopup`)を使う。認証ドメインが別(`medconf-iol-dev.firebaseapp.com`)で、リダイレクト方式は第三者ストレージの制限で失敗しやすいため(Firebase 公式の代替策の1つ)。コードの変更は今回は行わない。ポップアップは脆弱性ではなく、使い勝手とブロックの問題として実機で確かめる。
- 公開前に実機で確認すること: iPhone Safari・Android Chrome・PC で、(1) アカウントの選択、(2) 組織のポリシー・同意画面・MFA、(3) 別の画面(認証アプリ・メール)から戻ったときにポップアップが続くか、(4) キャンセル・ブロック時の案内とメールのリンクへの切り替え。今回の WebKit のブラウザテストは偽の SDK で、実 Microsoft のポップアップの試験ではない。
- 通常の利用を妨げる場合は、認証ドメインを同じドメインにする(`iol.medconf.jp` で `/__/auth/` を配信する)などのリダイレクト方式の対応を別途検討する。

## 既知の制限
- Microsoft のトークンにメールが入らないアカウントは使えない(安全側)。その場合はメールのリンクを使う。実アカウントでの確認が必要。
- 個人の Microsoft アカウントなど、承認済みのメールと違うアカウントは使えない(会社管理者の承認による例外は将来の検討事項)。
- `sign_in_provider` はログインした時点の値。会社側で Entra のアカウントを止めても Firebase のログイン状態は残るため、失効は担当者の無効化で行う。
