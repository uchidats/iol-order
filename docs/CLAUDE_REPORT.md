## 1. 立川病院の採用IOL 12件が「発注先未設定」の理由(読み取り専用の確認)
- 事実: 立川病院の `adoptedIols` 12件すべてで `dealerId` が未設定。ディーラーは `facilityDealers` に1件(栗原)だけ登録済み。
- 仕組み: 注文時(Cloud Functions `createOrder`)と確認画面は、「採用IOLの `dealerId` → その施設の `facilityDealers/{dealerId}`」で発注先を決める。**採用IOLに `dealerId` がなければ、ディーラーが登録されていても発注先は未設定**。ディーラー側の `dealerId` フィールド(グローバル連携用の別のID)は、この対応には使われない。
- **訂正(前回の報告)**: 前回「施設設定の『採用IOL』で発注先を設定する」と書いたが、**現在の施設設定には、採用IOLごとの発注先を選ぶ画面がない**(`dealerId` は保持されるだけで、画面・スクリプトのどちらからも設定できない。履歴上も一度も設定する実装はない)。
- 影響: このままでは、すべての注文の全明細が「発注先未設定」になる。発注メールのdry-runは、全明細が `unrouted` になり、メールが1通も生成されない。実送信は元々禁止・未実装なので、現時点で実害はないが、**実運用(メール発注)の前に必須**。
- 設定が必要な理由のまとめ: 発注先の決定(確認画面・注文の記録・メールの振り分け)の唯一の入力が、採用IOLの `dealerId` だから。
- 対応案(判断待ち。どれも今回は未実施):
  - A. 施設設定の採用IOLに「発注先」の選択を追加する(推奨。画面の追加+Rulesは既存のまま使える)。
  - B. メーカー単位で既定の発注先を一括設定できるようにする(A の補助)。
  - C. 管理スクリプトで一度だけ設定する(画面は作らない。実データ変更なので、dry-run・バックアップ付き)。
