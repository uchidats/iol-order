# ディーラー専用画面(第1段階: 閲覧)

設計の基準は [design/dealer-portal.md](design/dealer-portal.md)(Codex)。ここには実装した内容と、設計案からの変更点、デプロイの手順を書く。
**状態: 実装・自動テストまで(ブランチ `feature/dealer-portal`)。Codex のレビュー指摘(High 2・Medium 4・Low 1)に対応済み(下記)で、再レビュー待ち。本番への反映(Rules・Functions・画面)と機能の有効化は未実施で、再レビューとユーザーの承認後に行う。**

## 概要
- ディーラーの担当者は、別の入口 `dealer.html`(同じドメイン)から企業メールでログインする(既存のメールリンク認証。パスワード・Googleアカウントは不要)。
- 閲覧できるのは、**会社の担当者として有効 × 施設の管理者・副管理者が明示的に許可 × 自社宛ての明細** の注文だけ。許可より前の注文・テスト注文は対象外。
- 元の注文ドキュメントはブラウザへ渡さない。サーバー(callable)が自社宛ての明細だけを列挙して返す。共通備考・入力者・他社の明細・名称・宛先・通知・注文控えは返さない。
- 担当施設は表示の初期選択だけに使う(閲覧の権限ではない)。施設のチェックボックスで複数施設を選んで検索できる。
- ディーラーの担当者を施設の `members` に入れない(所属は会社の `staff`)。
- 注文の受付・メール送信は変更しない。受信の索引は注文の作成をきっかけに別のトリガーで作るため、ここが失敗・停止しても注文・メールは止まらない。
- 機能スイッチ `DEALER_PORTAL_ENABLED`(既定 false。注文受付・メールのスイッチとは別)。false の間、ディーラー用・施設用の API は「現在ご利用いただけません」を返し、索引は作らない。施設設定の項目も表示しない。運営者の管理 API は準備のため使える。

## データ(すべて新規。Rules でクライアントの直接の読み書きを拒否し、サーバーだけが扱う)
| 保存先 | 内容 |
| --- | --- |
| `dealerCompanies/{companyId}` | 会社名・状態(active/suspended)・`accessMode: companyWide`・`policyVersion: 1`(未知の方式・世代は拒否) |
| `dealerCompanies/{companyId}/branches/{branchId}` | 任意の支店(名前・状態)。支店なしでも使える |
| `dealerCompanies/{companyId}/staff/{uid}` | 担当者(承認済みのメール・氏名・役割 reader/companyAdmin・状態・任意の支店・担当施設 `facilityAssignments`(表示用)) |
| `dealerStaffIndex/{uid}` | 自分の所属会社の一覧(ログインした人の所属を引くため) |
| `dealerCompanyInvitations/{id}` | 参加待ち(会社・メール・役割・期限30日・状態)。本人のメールでのみ承諾できる |
| `facilities/{fid}/dealerPortalLinks/{localDealerId}` | 施設別発注先と会社の関連付け(運営者が作る)・状態(proposed/active/revoked)・現在の許可ID・revision |
| `dealerPortalGrants/{grantId}` | 施設が会社に与えた閲覧許可(許可の世代ごとに新しいID・開始時刻・取消・操作者と役割・開示方針) |
| `dealerCompanies/{companyId}/receipts/{receiptId}` | 受信の索引(1注文 × 1施設別発注先。自社分の件数・枚数・注文番号・注文日時と元注文の参照) |
| `dealerPortalAuditLogs/{id}` | 操作の記録(会社・担当者・関連付け・許可/取消・担当施設・索引の作り直し) |

## API(Cloud Functions)
- `dealerPortalApi`(担当者): `companies`(本人の有効な所属の会社) / `context`(会社・支店・閲覧できる施設・担当施設・初期選択) / `setAssignments`(自分の担当施設。許可済みの施設だけ) / `list`(期間・施設の複数選択・注文番号の完全一致・カーソル) / `get`(詳細) / `invitations` / `respond`。
- `facilityDealerPortal`(施設の管理者・副管理者): `status` / `grant` / `revoke`(revision で同時操作を検出)。
- `dealerPortalOperator`(運営者): `overview` / `createCompany` / `updateCompany` / `upsertBranch` / `inviteStaff` / `cancelInvitation` / `updateStaff`(無効化・役割・支店・担当施設の代行) / `proposeLink` / `reindex`(索引の作り直し。既定は確認のみ)。
- トリガー `indexDealerReceipts`(注文の作成時): 許可が有効・関連付けが一致・発注先が許可した時点と同じ・注文が許可の後・テストでない・発注先の矛盾がない場合だけ、冪等な ID で索引を作る。失敗は再試行(24時間まで)。

取得のたびに、ログイン(メール確認済み)・担当者が有効でメールが承認済みと一致・会社が有効・許可が有効で関連付けの現在の許可と一致・施設が有効・施設別発注先が存在し許可した時点と同じ・(詳細では)元注文が許可の後でテストでない、を確認する(キャッシュしない)。一覧は索引を読み、元注文は読み直さない(索引の作成時に除外済み)。取消・退職・会社の停止・施設の停止・発注先の削除の後は、次の取得から拒否する。他社・未許可の対象は「対象を表示できません」にまとめる。

## 画面
- `dealer.html`(ディーラー): ログイン → 参加の確認 → 受注一覧(期間・注文番号・医療機関のチェックボックス、「担当施設を選択」「閲覧可能施設をすべて選択」「選択を解除」、検索範囲の表示、担当施設として保存)→ 詳細(自社宛ての明細・注文メールの状態)。注文のデータは端末に保存しない。
- 施設設定「ディーラー画面での閲覧」(管理者・副管理者): 運営者が関連付けた発注先ごとに、共有範囲の説明を確認して許可・取消。
- メニュー「ディーラー画面の管理」(運営者): 会社・支店・担当者・関連付け。

## 設計案からの変更点(実装上の判断)
- 担当施設は staff 文書の配列 `facilityAssignments` に保存(サブコレクションにしない。1件の更新で済み、上限100件)。会社の方針は会社文書の `accessMode`・`policyVersion` に置いた。
- API は役割ごとに3つの callable にまとめ、`action` で操作を分けた(未知の操作・キーは拒否)。
- 一覧は会社の受信を注文日時の新しい順に走査し、施設・注文番号はサーバーで絞り込む(1回の要求で最大500件を走査。続きはカーソル)。複合インデックスは不要。件数が大きくなったら施設別の索引に切り替える。
- カーソルは会社・UID・検索条件・検索の基準時刻・有効期限(1時間)に結び付ける。暗号署名はしていないため、位置や期限の書き換え自体は防がないが、各行を毎回認可するため閲覧範囲は広がらない(改ざんをすべて拒否できるとは扱わない)。
- 入力者名・返信先メールは初版では返さない(設計 16 章の未決定事項。施設の開示設定を作るまで非表示)。

## Codex のレビュー(docs/reviews/dealer-portal-audit.md)への対応(2026-10-28)
| ID | 対応 |
| --- | --- |
| F-01 High | 許可(grant)に、許可した時点の発注先の指紋 `dealerFingerprint`(作成時刻・名称・宛名・発注用メール・連携ID)を保存。認可(`allowedScope`)と索引の作成で毎回照合し、一致しなければ公開も索引もしない。施設の画面には「停止中(取り消してから改めて許可)」と出す。並び順・使用報告用メールの変更では止めない。削除して同じ ID で作り直した場合も止まる |
| F-02 High | 担当者の無効化と同じトランザクションで、その会社・承認済みメール宛ての参加待ちを取り消す。承諾時は、同じ会社で同じメールの無効化済み担当者(別アカウントを含む)の無効化時刻 `disabledAt` より後に発行された案内だけを受け付ける。無効化の後に運営者が発行した案内での復帰はできる |
| F-03 Medium | 索引のトリガーは失敗を例外で知らせ、`retry: true` で再試行(ID が冪等なので重複しない)。2社のうち1社が失敗しても残りは作る。イベントから24時間を過ぎた再試行は打ち切ってログに残す。運営者の作り直し(`reindex`)は上限ごとに続きの位置 `nextCursor` を返し、最後まで到達できる。注文・メールの処理には関与しない |
| F-04 Medium | カーソルに検索の基準時刻(最初のページを読んだ時点)を持たせ、続きを読むときに、その後に作られた索引が読み終えた範囲に入っていれば `restart: true` を返す。画面は「先頭から検索し直してください」と案内する(欠けたまま全件表示としない)。未読の範囲に入った索引は続きでそのまま読める |
| F-05 Medium | 施設・期間・注文番号・選択ボタンの変更で、表示中の結果と続きを破棄(「さらに表示」を出さない)。通信中に条件が変わった応答は表示しない(検索の世代)。あわせて、`.btn` の表示指定で「さらに表示」が `hidden` でも見えていた不具合を直した |
| F-06 Medium | 会社を指定しないときは、所属の一覧のうち、いま有効な所属(会社が有効・担当者が有効・メール一致)だけから選ぶ。有効な所属が2社以上なら、新しい `companies`(本人の有効な所属の会社名とIDだけ)で画面に会社の選択を出す |
| F-07 Low | 走査の途中で0件(続きあり)のときは「該当なし」とせず、「さらに表示で続きを検索できます」と表示する |

カーソルの形式は v2(基準時刻を含む)。v1 のカーソルは「検索をやり直してください」になる(未公開のため影響なし)。基準時刻の検知は続きを読むときに行うため、最後のページの読み取り中に入った索引は、次の検索で表示される。

## 今回含めないもの
注文票・一覧の印刷、Excel・CSV出力、会社管理者による担当者管理の画面、受注確認ステータス、過去注文の取り込み、支店・担当者単位の閲覧権限。

## デプロイ(承認後。この順で)
1. Firestore Rules(新しい領域の明示的な拒否): `firebase deploy --only firestore:rules`。既存のルールは変更なし(追加のみ)。
2. Functions: `dealerPortalApi`・`facilityDealerPortal`・`dealerPortalOperator`・`indexDealerReceipts`(新規)。`DEALER_PORTAL_ENABLED` は既定の false のまま。新しいトリガーの Cloud Run サービス `indexdealerreceipts` だけに、関数の実行アカウントの `roles/run.invoker` を付ける。
3. 画面(`main` へ取り込み)。機能が止まっている間は、施設設定の項目は表示されない。`dealer.html` は「現在ご利用いただけません」。
4. 運営者が試験の会社・担当者・関連付けを登録し、`DEALER_PORTAL_ENABLED=true` にして Functions を再デプロイ。施設の管理者・副管理者が許可した後の新規注文から表示される。
5. 停止するときは `DEALER_PORTAL_ENABLED=false`(注文・メールには影響しない)。
