# ディーラー専用画面(第1段階: 閲覧)

設計の基準は [design/dealer-portal.md](design/dealer-portal.md)(Codex)。ここには実装した内容と、設計案からの変更点、デプロイの手順を書く。
**状態: 実装・自動テストまで(ブランチ `feature/dealer-portal`)。Codex のレビュー指摘(High 2・Medium 4・Low 1)、再レビューの残り3件、再々レビューの残り3件に対応済み(下記)。本番への反映(Rules・Functions・画面)と機能の有効化は未実施で、再レビューとユーザーの承認後に行う。**

## 概要
- ディーラーの担当者は、別の入口 `dealer.html`(同じドメイン)から「Googleでログイン」「Microsoftでログイン」「メールアドレスでログイン(リンク)」のいずれかでログインする。初めて使うログイン方法(参加を含む)は、承認済みのメールに届く確認コードで担当者に紐付け、以後は紐付けた認証主体だけを通す(「ログインと本人確認」)。会社の所属・施設の許可はサーバーが毎回確かめる。
- 閲覧できるのは、**会社の担当者として有効 × 施設の管理者・副管理者が明示的に許可 × 自社宛ての明細** の注文だけ。許可より前の注文・テスト注文は対象外。
- 元の注文ドキュメントはブラウザへ渡さない。サーバー(callable)が自社宛ての明細だけを列挙して返す。共通備考・入力者・他社の明細・名称・宛先・通知・注文控えは返さない。
- 担当施設は表示の初期選択だけに使う(閲覧の権限ではない)。施設のチェックボックスで複数施設を選んで検索できる。
- ディーラーの担当者を施設の `members` に入れない(所属は会社の `staff`)。
- 注文の受付・メール送信は変更しない。受信の索引は注文の作成をきっかけに別のトリガーで作るため、ここが失敗・停止しても注文・メールは止まらない。
- 機能スイッチ `DEALER_PORTAL_ENABLED`(既定 false。注文受付・メールのスイッチとは別)。false の間、ディーラー用・施設用の API は「現在ご利用いただけません」を返し、索引は作らない。施設設定の項目も表示しない。運営者の管理 API は準備のため使える。

## API(Cloud Functions)
- `dealerPortalApi`(担当者): `companies`(本人の有効な所属の会社) / `context`(会社・支店・閲覧できる施設・担当施設・初期選択) / `setAssignments`(自分の担当施設。許可済みの施設だけ) / `list`(期間・施設の複数選択・注文番号の完全一致・カーソル) / `get`(詳細) / `sendCode`・`verifyCode`(本人確認。参加を含む)。
- `dealerPortalApi` の `week`(手術日の週表示。`weekStart`=月曜の日付・`facilityFilter`): 受信の索引の `surgeryDates`(自社宛ての明細の手術日。`indexDealerReceipts` が作成し、作り直しで既存の索引にも補う)で、その週(月曜〜日曜)に手術日がある受信を最大100件読み、詳細と同じ確認(許可・関連付け・許可の後・テストでない・注文時点の発注先)を通ったものだけ、その週の自社宛ての明細(メーカー・型番・度数・枚数)を手術日ごとに返す。1つの注文に手術日が複数あれば、各週・各日にその日の明細だけ(注文番号は同じ。`otherDates` でほかの手術日を示す)。超えたら `truncated`。施設側の手術日の索引(orderSurgeryIndex)は他社の注文を含み、論理削除の扱いも受信の一覧と異なるため使わない。
- `facilityDealerPortal`(施設の管理者・副管理者): `status` / `grant` / `revoke`(revision で同時操作を検出)。
- `dealerPortalOperator`(運営者): `overview` / `createCompany` / `updateCompany` / `upsertBranch` / `inviteStaff` / `cancelInvitation`(`staffId`) / `updateStaff`(`staffId`。無効化・役割・支店・担当施設の代行) / `proposeLink` / `reindex`(索引の作り直し。既定は確認のみ)。
- トリガー `indexDealerReceipts`(注文の作成時): 許可が有効・関連付けが一致・発注先が許可した時点と同じ・注文が許可の後・テストでない・発注先の矛盾がない場合だけ、冪等な ID で索引を作る。失敗は再試行(24時間まで)。

取得のたびに、今回のログインの認証主体が紐付け済みで世代が一致・担当者が有効でログインのメールが承認済みと一致・会社が有効・許可が有効で関連付けの現在の許可と一致・施設が有効・施設別発注先が存在し許可した時点と同じ・(詳細では)元注文が許可の後でテストでない、を確認する(キャッシュしない)。一覧は索引を読み、元注文は読み直さない(索引の作成時に除外済み)。取消・退職・会社の停止・施設の停止・発注先の削除の後は、次の取得から拒否する。他社・未許可の対象は「対象を表示できません」にまとめる。

## 画面
- 受注一覧の表示: 初期表示は「手術日(週)」の今週(日本時間の月曜〜日曜)。「← 前週」「今週」「翌週 →」で移動。手術日ごとに、医療機関・注文番号・明細(メーカー・型番・度数・枚数)・注文日時、ほかの手術日がある注文は「同じ注文のほかの手術日」を表示。「注文日順」で従来の一覧(期間・注文番号で検索)へ切り替え。医療機関の選択は両方で共通(週表示は選択を変えるとすぐ読み直す)。
- `dealer.html`(ディーラー): ログイン → 本人確認(初めてのログイン方法・参加・新しいブラウザのとき)→ 受注一覧(期間・注文番号・医療機関のチェックボックス、「担当施設を選択」「閲覧可能施設をすべて選択」「選択を解除」、検索範囲の表示、担当施設として保存)→ 詳細(自社宛ての明細・注文メールの状態)。注文のデータは端末に保存しない。
- 施設設定「ディーラー画面での閲覧」(管理者・副管理者): 運営者が関連付けた発注先ごとに、共有範囲の説明を確認して許可・取消。
- メニュー「ディーラー管理」(運営者): 会社・支店・担当者・関連付け。

## 設計案からの変更点(実装上の判断)
- 担当施設は staff 文書の配列 `facilityAssignments` に保存(サブコレクションにしない。1件の更新で済み、上限100件)。会社の方針は会社文書の `accessMode`・`policyVersion` に置いた。
- API は役割ごとに3つの callable にまとめ、`action` で操作を分けた(未知の操作・キーは拒否)。
- 一覧は会社の受信を注文日時の新しい順に走査し、施設・注文番号はサーバーで絞り込む(1回の要求で最大500件を走査。続きはカーソル)。複合インデックスは不要。件数が大きくなったら施設別の索引に切り替える。
- カーソルは会社・UID・検索条件・検索の基準時刻・有効期限(1時間)に結び付ける。暗号署名はしていないため、位置や期限の書き換え自体は防がないが、各行を毎回認可するため閲覧範囲は広がらない(改ざんをすべて拒否できるとは扱わない)。
- 入力者名・返信先メールは初版では返さない(設計 16 章の未決定事項。施設の開示設定を作るまで非表示)。

## ログインと本人確認(担当者 ID × 認証主体のホワイトリスト。2026-10-28)
これまでのレビュー(G-01〜G-04・MS-01〜MS-03・統合版の最終レビューの MS-01)を受け、UID を担当者の主キーにする設計から、次の設計に作り直した(ブランチ `feature/dealer-auth-bindings`)。

### 担当者と認証主体
- 担当者は `dealerStaff/{staffId}`。`staffId` は「会社×承認済みのメール」から決まり(`dstf_` + ハッシュ)、Firebase の UID ではない。招待もこの文書の状態(`invited` → `active`、取り消しは `cancelled`、無効化は `disabled`)で表す。同じ会社・同じメールの担当者はデータの構造上1人だけ(旧 G-03 の重複チェック・運営者の警告・UID の移行の手順は不要)。
- 閲覧は「今回のログインの認証主体」と「確認したブラウザ(端末の値)」の両方が、確認コードで担当者に紐付けたもの(`dealerAuthBindings`)に入っているときだけ通す(ホワイトリスト)。
- 確認したブラウザは、どの方式でも必要(AB-02。`docs/reviews/dealer-auth-bindings-audit.md`)。更新したトークンの `identities` は、そのセッションで認証したアカウントではなく、UID に「いま」連携されているアカウントを示すことがある(未登録の Microsoft B の古い更新トークンが、B を外して A を紐付けた後に A を名乗る。エミュレータで再現)。トークンだけではセッションの本人を決められないため、確認コードを確かめたブラウザにサーバーが値を発行して結び付ける。Google・Microsoft も、新しいブラウザ(端末)では確認コードが1回必要(以後180日)。
- 端末の値は、発行したときの認証主体(Google・Microsoft はその固有ID、メールリンクは「メールリンク」)に結び付け、閲覧では今回の主体と同じ主体に発行した値だけを認める(再レビュー AB-02)。Google・Microsoft に発行した値は password(メールリンク)のログインや別の主体に使えない。同じ方式の別の主体に置き換えると、置き換えた主体の紐付けとその主体に発行した値も消す。画面の保存も、UID・ログイン方法・主体ごとのキーに分け、「この端末を記憶する」を外すと保存しない(共用のパソコン)。UID・メールの一致・同じ UID に連携されたほかのプロバイダー・`email_verified` だけでは通さない。

| ログイン | 認証主体(サーバーがトークンから決める) | 条件(満たさなければ拒否。推測で補わない) |
| --- | --- | --- |
| Google | `google:{固有ID}` | `sign_in_provider` が `google.com`、`identities["google.com"]` がちょうど1つ、`email_verified` が true |
| Microsoft | `microsoft:{固有ID}` | `sign_in_provider` が `microsoft.com`、`identities["microsoft.com"]` がちょうど1つ、メールが取れること(`email_verified` は問わない。紐付けの確認コードを証明にする) |
| メールリンク | `device:{端末の値のハッシュ}` | `sign_in_provider` が `password`、`email_verified` が true。パスワードのログインと区別できないため、端末の値そのものを認証主体とする |

- どの方式でも、ログインのメールが担当者の承認済みのメールと一致するときだけ使える(個人の Gmail など、別のメールのアカウントは今回は使えない。会社管理者の承認による例外は将来の検討事項)。
- 紐付けは担当者の世代(`authRevision`)と一致するときだけ有効。無効化・再招待で世代を進めると、その担当者の Google・Microsoft・メールリンクの紐付けがすべて一度に失効する。有効に戻した後は確認コードで紐付け直す。
- Firebase のアカウントの連携・解除(`linkWithPopup`・`unlink`)は使わない。ログイン方法ごとに同じ UID でも別の UID でもよい(サーバーの紐付けで同じ担当者になる)。未登録の Microsoft が既存の UID に自動で結び付いても、その後パスワードを設定・連携を解除して入り直しても、認証主体が未登録なので閲覧できない(エミュレータで再現して確認)。

### 確認コード(参加・初めてのログイン方法・新しいブラウザで共通)
- `sendCode`: 送り先はログインのメール。サーバーが、期限内の招待か有効な所属のある担当者(会社ごとに個別に確認)と照合して確定する(画面からは送り先を受け取らない)。対象を「会社・担当者・世代・状態」で記録する(AB-01)。この要求では送らず、送信の依頼(`dealerAuthCodeJobs`)を作るだけ(再レビュー AB-03)。コードの生成と送信は、依頼をきっかけに動くトリガー `deliverDealerAuthCode` が行う(再試行しない。利用者が送り直す)。このため、登録の有無・送信の成否・送信の待ち時間で応答が変わらない。対象がなければ送らない(照合の結果は登録がある場合と同じ)。送信の結果は記録だけする。トリガーは送る直前に、対象の担当者(状態・世代・承認済みのメール・招待の期限)と会社の状態を読み直し、取消・無効化・会社の停止の後は送らない。送信の依頼には5分の期限があり、期限を過ぎた依頼からはコードを作らない。メールに会社名を書く(画面には確認まで会社名を出さない)。
- `verifyCode`: 同じトランザクションで、コードを消費し、送った時点の対象のうち、いまも同じ世代・同じ状態の担当者だけについて(AB-01。無効化→再有効化・無効化→再招待の後、送信の後に届いた招待には使わない)、招待を承諾し、今回の認証主体と確認したブラウザ(端末の値。1回だけ返す)を紐付ける。Google・Microsoft は担当者ごとに1つ(置き換え)。端末は担当者ごとに10台まで。
- コード: 8桁(`crypto.randomInt`)・ソルト付きハッシュ・定時間の比較。認証主体(メールリンクは UID)・メールに結び付き、10分・1回・誤り5回まで。送り直しは1分あけ、認証主体ごとに24時間で5回・送り先のメールごとに24時間で10回まで(`dealerAuthChallenges`)。送信回数と最後の送信時刻は、コードを使っても消えない(AB-05)。同時の照合・送信もトランザクションで1回だけ。
- 送信は注文メールと同じ設定(Resend)に従う。送信の停止中・テスト用の宛先だけへの送信中は、本人にコードが届かないため確認できない(安全側)。エミュレータのテストだけ、`demo-` のプロジェクトでコードをテスト用の文書に書く。
- 画面は「本人確認」の1画面だけ(確認コードを送る → 入力 → 受注一覧)。端末の値をブラウザに保存できない場合(保存領域の取得自体が拒否される場合を含む)も、この画面を開いている間はメモリの値で使え、保存できなかったことを表示する(次のログインでは確認し直す。AB-04)。確認済みの会社があるときに新しい参加の案内が届いていれば「参加の確認」を出し、「あとで」で受注一覧へ進める。「参加しない」ボタンはない(招待の取り消しは運営者)。

### 医療機関の画面とのセッションの分離
- `dealer.html` は Firebase のアプリを別の名前(`dealer-portal`)で初期化する。同じオリジン・同じプロジェクトでも、ログイン状態の保存先が分かれ、ディーラー画面のログイン・ログアウトが医療機関の画面のログインを切り替えない。メールリンクの保存キーも分ける(`iol_dealer_emaillink_pending`)。

### 運営者の操作
- 担当者は `staffId` で指定する(`updateStaff`・`cancelInvitation`)。参加済み(有効)の担当者は招待できない(設定は `updateStaff`)。運営者画面には各担当者の紐付け済みのログイン方法(Google・Microsoft・メール(確認済みの端末))を表示する。

### 制限
- サーバーが判断に使えるのはトークンに載る情報(今回のログイン方法とその固有ID)だけ。`sign_in_provider` はログインした時点の値で、トークンを更新しても変わらない。会社側で Google・Entra のアカウントを止めても、Firebase のログイン状態は残るため、失効は担当者の無効化で行う。
- メールリンクの端末の値はブラウザの保存領域にあり、端末そのものの乗っ取りは防げない(担当者の無効化で失効)。送信回数の上限に達すると、その間は確認できない。

### 停止中(`DEALER_PORTAL_ENABLED=false`)の注意
- Google・Microsoft・メールのリンクの認証そのものは、このスイッチでは止まらない(医療機関の画面と認証を共用)。`dealer.html` を配信していればログイン画面は動くが、ログイン後はサーバーがすべての取得を拒否し、「現在ご利用いただけません」とログアウトだけを表示する(会社・施設・注文は出ない)。施設側の状態の確認と取消は停止中も可能(N-01)。
- 認証の操作まで止めたまま配備する場合は、`dealer.html` の公開そのものを別に制御する。

### Microsoft ログイン
- 「Microsoftでログイン」(Firebase 標準の `OAuthProvider("microsoft.com")`。ポップアップ)。ほかの方式と同じく、初回は確認コードで紐付けた Microsoft の固有IDだけが使える。設定手順・安全上の扱いは [dealer-microsoft-login.md](dealer-microsoft-login.md)。

### 発注先の一括保存と Rules の参照回数(統合版の最終レビューの Low。今回は変更なし)
- 閲覧を許可中の発注先のロック(F-01)のため、発注先の作成・更新ごとに Rules が関連付けの文書を参照する。1回のバッチの参照回数の上限(20)により、多数の発注先を一度に新規作成するとバッチ全体が拒否され得る(Codex の比較で、新規25件は main で成功・統合版で拒否)。既存の発注先の並べ替えの再保存(25件)は成功を確認済み。通常の画面は行ごとに確定・自動保存する。
- 対応案(採否はユーザーが決める): 保存を小さいバッチ(例: 8件ずつ)に分け、途中で失敗したら再読み込みして続きから保存する。またはサーバーの処理で保存する。F-01 のロックは外さない。大量の一括追加・識別項目の一括更新を提供する前に対応する。

### 有効化の前に確認すること(利用者・運営者)
1. 本番の Firebase Console のアカウントのリンク設定・有効な認証方式・承認済みドメイン(既定値と決め付けない。変更は医療機関の画面にも及ぶ)。
2. 承認された実アカウントで、Workspace の主アドレス・Gmail 以外の企業メール・別名、Microsoft の企業・個人・ゲストのアカウントでの、トークンの `sign_in_provider`・固有ID(毎回同じ値か)・メールの有無、同じメールの既存アカウントとの関係(自動で結び付くか・競合・別の UID)。実トークンは記録しない。
3. 実際のポップアップ(第三者 Cookie・Safari・スマートフォン・組織のポリシー)、メールのリンクの到達と別端末での完了、医療機関の画面との同時利用・ログアウト。

## デプロイ(承認後。この順で)
0. 配備の前に、このブランチを最新の `main` に統合し、統合した結果でバージョン付与(`stamp-assets`)と関連テストを確認する(`main` 側の注文画面・マニュアルの変更を戻さないため)。
1. Firestore Rules: `firebase deploy --only firestore:rules`。新しい領域の明示的な拒否に加えて、**既存の発注先(facilityDealers)の作成・更新・削除の条件も変わる**(閲覧を許可中の発注先の識別項目のロック)。「追加のみ」ではないので、本番との差分を確認してから配備する。
