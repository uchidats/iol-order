# ディーラー専用画面(第1段階: 閲覧)

設計の基準は [design/dealer-portal.md](design/dealer-portal.md)(Codex)。ここには実装した内容と、設計案からの変更点、デプロイの手順を書く。
**状態: 実装・自動テストまで(ブランチ `feature/dealer-portal`)。Codex のレビュー指摘(High 2・Medium 4・Low 1)、再レビューの残り3件、再々レビューの残り3件に対応済み(下記)。本番への反映(Rules・Functions・画面)と機能の有効化は未実施で、再レビューとユーザーの承認後に行う。**

## 概要
- ディーラーの担当者は、別の入口 `dealer.html`(同じドメイン)からログインする。「Googleでログイン」(医療機関の画面と同じ認証サービス。毎回アカウントの選択画面を出す)と、企業メールへのログインリンク(パスワード不要)。会社への参加(招待の承諾)は、ログイン方法にかかわらず、招待されたメールに届く確認コード(サーバーが発行・照合)で行う。どちらでも、招待先のメールとの一致・会社の所属・施設の許可はサーバーが確認済みのメールと UID で毎回確かめる(Rules・Functions はログイン方法に依存しない)。
- 閲覧できるのは、**会社の担当者として有効 × 施設の管理者・副管理者が明示的に許可 × 自社宛ての明細** の注文だけ。許可より前の注文・テスト注文は対象外。
- 元の注文ドキュメントはブラウザへ渡さない。サーバー(callable)が自社宛ての明細だけを列挙して返す。共通備考・入力者・他社の明細・名称・宛先・通知・注文控えは返さない。
- 担当施設は表示の初期選択だけに使う(閲覧の権限ではない)。施設のチェックボックスで複数施設を選んで検索できる。
- ディーラーの担当者を施設の `members` に入れない(所属は会社の `staff`)。
- 注文の受付・メール送信は変更しない。受信の索引は注文の作成をきっかけに別のトリガーで作るため、ここが失敗・停止しても注文・メールは止まらない。
- 機能スイッチ `DEALER_PORTAL_ENABLED`(既定 false。注文受付・メールのスイッチとは別)。false の間、ディーラー用・施設用の API は「現在ご利用いただけません」を返し、索引は作らない。施設設定の項目も表示しない。運営者の管理 API は準備のため使える。

| `dealerCompanyInvitations/{id}` | 参加待ち(会社・メール・役割・期限30日・状態)。本人のメールでのみ承諾できる |

| `dealerPortalGrants/{grantId}` | 施設が会社に与えた閲覧許可(許可の世代ごとに新しいID・開始時刻・取消・操作者と役割・開示方針) |

## API(Cloud Functions)
- `dealerPortalApi`(担当者): `companies`(本人の有効な所属の会社) / `context`(会社・支店・閲覧できる施設・担当施設・初期選択) / `setAssignments`(自分の担当施設。許可済みの施設だけ) / `list`(期間・施設の複数選択・注文番号の完全一致・カーソル) / `get`(詳細) / `invitations` / `respond`。
- `facilityDealerPortal`(施設の管理者・副管理者): `status` / `grant` / `revoke`(revision で同時操作を検出)。
- `dealerPortalOperator`(運営者): `overview` / `createCompany` / `updateCompany` / `upsertBranch` / `inviteStaff` / `cancelInvitation` / `updateStaff`(無効化・役割・支店・担当施設の代行) / `proposeLink` / `reindex`(索引の作り直し。既定は確認のみ)。
- トリガー `indexDealerReceipts`(注文の作成時): 許可が有効・関連付けが一致・発注先が許可した時点と同じ・注文が許可の後・テストでない・発注先の矛盾がない場合だけ、冪等な ID で索引を作る。失敗は再試行(24時間まで)。

取得のたびに、ログイン(メール確認済み)・担当者が有効でメールが承認済みと一致・会社が有効・許可が有効で関連付けの現在の許可と一致・施設が有効・施設別発注先が存在し許可した時点と同じ・(詳細では)元注文が許可の後でテストでない、を確認する(キャッシュしない)。一覧は索引を読み、元注文は読み直さない(索引の作成時に除外済み)。取消・退職・会社の停止・施設の停止・発注先の削除の後は、次の取得から拒否する。他社・未許可の対象は「対象を表示できません」にまとめる。

## 画面
- `dealer.html`(ディーラー): ログイン → 参加の確認 → 受注一覧(期間・注文番号・医療機関のチェックボックス、「担当施設を選択」「閲覧可能施設をすべて選択」「選択を解除」、検索範囲の表示、担当施設として保存)→ 詳細(自社宛ての明細・注文メールの状態)。注文のデータは端末に保存しない。
- 施設設定「ディーラー画面での閲覧」(管理者・副管理者): 運営者が関連付けた発注先ごとに、共有範囲の説明を確認して許可・取消。
- メニュー「ディーラー画面の管理」(運営者): 会社・支店・担当者・関連付け。

## 設計案からの変更点(実装上の判断)
- 担当施設は staff 文書の配列 `facilityAssignments` に保存(サブコレクションにしない。1件の更新で済み、上限100件)。会社の方針は会社文書の `accessMode`・`policyVersion` に置いた。
- API は役割ごとに3つの callable にまとめ、`action` で操作を分けた(未知の操作・キーは拒否)。
- 一覧は会社の受信を注文日時の新しい順に走査し、施設・注文番号はサーバーで絞り込む(1回の要求で最大500件を走査。続きはカーソル)。複合インデックスは不要。件数が大きくなったら施設別の索引に切り替える。
- カーソルは会社・UID・検索条件・検索の基準時刻・有効期限(1時間)に結び付ける。暗号署名はしていないため、位置や期限の書き換え自体は防がないが、各行を毎回認可するため閲覧範囲は広がらない(改ざんをすべて拒否できるとは扱わない)。
- 入力者名・返信先メールは初版では返さない(設計 16 章の未決定事項。施設の開示設定を作るまで非表示)。

## Googleログイン(2026-10-28。Codex のレビュー docs/reviews/dealer-google-login-audit.md を反映)
- 画面: ログイン画面の上段に「Googleでログイン」(毎回アカウントの選択画面)、下段にメールリンク(パスワード不要)。失敗(キャンセル・ポップアップのブロック・別のログイン方法で登録済み・通信)は案内を出す。Microsoft ログインは未実装。

### 参加(会社への所属の付与)の条件(G-02・G-02-R1)
- 招待の承諾は、**サーバーが発行し、招待されたメールアドレスへ送った確認コード**を入力した場合だけ受け付ける。ログイン方法(メールのリンク・パスワード・Google・Microsoft)、トークンの `email_verified`、UID、メールの一致は、メールを今受け取れることの証明として扱わない。
  - 理由(G-02-R1): メールのリンクと通常のパスワードのログインは、トークン上どちらも `sign_in_provider: "password"` で区別できない。Google のセッションでパスワードを設定して入り直すと、`email_verified: true`・直近の `auth_time` の `password` トークンが得られ、旧方式(30分以内の `password` を受信の証明とみなす)では承諾から注文の閲覧まで進めた(Codex の再現)。
- 確認コード(`sendCode` → `respond` の `code`):
  - 8桁の数字(`crypto.randomInt`)。招待の文書にはソルト付きのハッシュだけを保存し、照合は定時間の比較。
  - 要求した UID・メール・招待の世代(作成時刻)に結び付ける。別の UID・別の招待・作り直した招待では使えない。
  - 有効期限10分、1回だけ(承諾と同じトランザクションで削除)。誤り5回で無効。送り直しは1分あけ、1つの招待で5回まで。送信は監査記録 `staff.joinCodeSent` に残す(コードは残さない)。
  - 送信は注文メールと同じ送信の設定(Resend)。`MAIL_SENDING_ENABLED` が false なら送れず参加できない。`MAIL_TEST_ONLY` が true の間はテスト用の宛先に届くため、本人は参加できない(有効化の前に確認する)。メールに会社名を書く。
  - エミュレータのテストだけは、`demo-` のプロジェクトで `DEALER_JOIN_CODE_TEST_SINK=true` のとき、コードをテスト用の文書 `dealerJoinCodeTestSink` に書く(本番の環境ファイルには書かない)。
- 招待の一覧は、メールの受信を確かめる前なので会社名を返さない(招待 ID と役割だけ)。辞退はコードなしでできる。
- 参加した後の閲覧は、ログイン方法に依存しない(UID・承認済みのメール・会社と施設の許可を毎回確認)。メールが未確認(false・欠落・文字列)のアカウントはすべて拒否。
- ログイン方法を変えて別の UID になった場合: その UID には所属がないので閲覧できない。所属を使うには、同じ会社の同じメールの有効な旧 UID を運営者が無効化し、再招待のうえ新しい UID で確認コードを受け取って承諾する(G-03)。無効化した旧 UID が再招待を先取りしようとしても、コードは招待されたメールにだけ届く。

### UID の扱い(G-01)
- 所属は UID(`staff/{uid}`)に結び付く。Google とメールのリンクで同じ UID になるのは、Firebase が同じユーザーに結び付けられる場合だけで、**自動的に同じになるとは前提にしない**。Firebase の「同じメールアドレスのアカウントをリンクする」設定でも、Google が信頼できるプロバイダーでないメール(Gmail 以外で Google が管理しない企業メールなど)では、自動では結び付かず `auth/account-exists-with-different-credential`(競合)になり得る。「同じメールで複数アカウント」設定では別の UID になり得る。Workspace の別名(エイリアス)は主アドレスと別のメールとして扱う。
- 本システムは明示的なアカウント連携(`linkWithCredential`)を実装しない。Google で所属が使えない(競合・別の UID)場合は、**参加したときのログイン方法を続ける**運用とする。別の UID になっても、その UID には所属がないため閲覧できない(権限は増えない)。
- Auth エミュレータの E2E では、既定の設定・模擬トークンで「メールのリンクで参加 → Google でも同じ UID で所属を使える」ことを確認した。本番の設定・Google の管理主体・既存アカウントでの動作は、承認された実アカウントでの確認が必要。

### 別の UID への移行・退職(G-03)
- 同じ会社に、同じメールの**有効な**別アカウント(UID)があれば、新しい UID での参加と、旧 UID の「有効に戻す」をサーバーが拒否する(同じメールの有効な UID を2つにしない)。メールの一致だけで所属・医療機関の所属・カスタムクレームを新しい UID へ移すことはしない。
- 正式な移行の手順: (1) 運営者画面で、同じメールのすべてのアカウントを確認する(各担当者にアカウントの識別と「同じメールアドレスの別のアカウントが N 件」の警告を表示) → (2) 旧 UID を無効化する(同じメール宛ての参加待ちも同時に取り消す) → (3) 改めて招待する → (4) 本人が新しい UID でログインし、招待されたメールに届いた確認コードで承諾する。
- 退職・異動: 同じメールのすべての UID を無効化し、参加待ちが残っていないことを確認する。

### 停止中(`DEALER_PORTAL_ENABLED=false`)の注意
- Google ログイン・メールのリンクの認証そのものは、このスイッチでは止まらない(医療機関の画面と認証を共用)。`dealer.html` を配信していればログイン画面は動くが、ログイン後はサーバーがすべての取得を拒否し、「現在ご利用いただけません」とログアウトだけを表示する(会社・施設・注文は出ない)。施設側の状態の確認と取消は停止中も可能(N-01)。
- 認証の操作まで止めたまま配備する場合は、`dealer.html` の公開そのものを別に制御する。

### Microsoft ログイン
- 「Microsoftでログイン」(Firebase 標準の `OAuthProvider("microsoft.com")`)。参加は他のログインと同じく確認コードで行う。Microsoft が連携された UID は、ログイン方法にかかわらず、本人が承認済みのメールの確認コードで登録した Microsoft アカウントでなければ閲覧できない(メールの一致・UID の結び付け・ログイン方法だけでは不可)。設定手順・安全上の扱いは [dealer-microsoft-login.md](dealer-microsoft-login.md)。

### 有効化の前に確認すること(利用者・運営者)
1. 本番の Firebase Console のアカウントのリンク設定・有効な認証方式・承認済みドメイン(既定値と決め付けない。変更は医療機関の画面にも及ぶ)。
2. 承認された実アカウントで、Workspace の主アドレス・Gmail 以外の企業メール・別名での、Google とメールのリンクの切り替え(UID・競合・所属)。実トークンは記録しない。
3. 実際のポップアップ(第三者 Cookie・Safari・スマートフォン・組織のポリシー)、メールのリンクの到達と別端末での完了、医療機関の画面との同時利用・ログアウト。

## デプロイ(承認後。この順で)
0. 配備の前に、このブランチを最新の `main` に統合し、統合した結果でバージョン付与(`stamp-assets`)と関連テストを確認する(`main` 側の注文画面・マニュアルの変更を戻さないため)。
