# 担当医(明細ごと)と実際の発注者

## 用語
- **担当医**: そのレンズを使う手術の担当医。施設設定の「担当医」マスターから、**レンズ(明細)ごとに**選ぶ。旧「注文者」マスターを名称変更したもので、**保存先は互換性のため従来の `facilities/{fid}/orderers` コレクションのまま**(新しいマスターは作らない。登録済みの氏名・メール・並び順はそのまま使われる)。登録項目は「氏名(必須)」「メールアドレス(任意)」。有効/無効はない。
- **実際の発注者**: Google ログインしたアカウント。**サーバーが認証情報から** `createdBy`(uid / email / displayName)に記録する。クライアントが申告した発注者・代理発注の項目は受け付けない(未知のキーとして拒否)。「代理発注」のチェックも、発注者の手入力欄もない。

## 画面
- 注文全体の「注文者」欄は無い。各レンズの「手術日」の直下に、必須の「担当医」。
- 「＋レンズを追加」で、直前のレンズの担当医と手術日を引き継ぐ(変更可)。担当医が異なる複数のレンズも、1回の注文で扱える。同じレンズ・度数・手術日でも、担当医が違えば別の明細。
- 確認画面は、レンズごとに「担当医・手術日・発注先ディーラー」を表示する。発注先は、採用IOLに設定されたディーラーが、この施設に今も登録されている場合だけ(無ければ「未設定」)。

## データ(`createOrder`)
- リクエスト: `lines[i].doctorId`(担当医ID)だけを送る。氏名・メールはサーバーが担当医マスターから引く。
- 保存(`schemaVersion: 3`): 各明細に `doctor: {id, name, email|null}`(スナップショット)、注文全体に `doctorIds`(含まれる担当医)。**注文全体の `orderer` は作らない。** 実際の発注者は `createdBy`。
- 検証: 担当医は明細ごとに、この施設のマスターに存在すること(他施設・存在しない → 「明細N: 担当医が見つかりません」で注文全体を拒否)。重複判定・冪等性(同じ `requestId` で担当医が変わると拒否)は担当医も含めて判定する。
- 旧形式との互換:
  - 旧クライアント(トップレベルの `ordererId`)は、担当医を指定していない全明細の担当医として扱う。
  - 読み込み(`orderLinesOf`): 旧形式(注文全体の `orderer`)の注文は、各明細の担当医として読める。既存の注文は書き換えない。

## 注文履歴での追跡
各明細の `doctor`(担当医)と、注文の `createdBy`(実際の発注者)を別々に追跡できる。担当医が異なる明細も、明細ごとに正しく残る。

## 反映上の注意
Cloud Functions(`createOrder`)を先にデプロイし、続けて画面を反映する(旧画面は `ordererId`、新画面は `doctorId`。サーバーは両方受け付ける)。Rules の変更はない。移行作業は不要(既存の担当医マスターをそのまま使う)。
