## 0. 決定事項(2026-11-03、ユーザー)

1. **ディーラーへの共有と閲覧は第1段階**に含める。今回の最重要目的は、医師が手術室から外来へ台紙を運ばなくても、ディーラーが写真を確認できること。
2. **アクセスコードは毎回入力**する(端末に記憶しない)。コードは**施設管理者・副管理者**が設定する**半角数字6桁以上**。
3. **撮影画像の圧縮条件(長辺 3000px など)は保留**。シールの細かな文字・シリアル番号の判読を優先し、実機検証の後に決める。それまでは撮影した解像度のまま送る前提で設計する。(→ 改訂7の決定 21 で確定)
4. **既存の台紙の使い方はなるべく変えない**。台紙に施設専用の **QR コードを貼る**だけで対応する。(改訂7: 新しい台紙の印刷は任意。既存の台紙に QR を貼る使い方も残す)
5. **アクセスコードは台紙に記載・印刷しない**。台紙に貼るのは QR コードだけで、QR にもコードを含めない。QR・台紙の印刷画面にもコードを載せない。コードは施設管理者・副管理者が設定し、看護師へ別途共有する。看護師は QR を読み取った後、毎回コードを入力して送信する。

追加の決定(2026-11-03、ユーザー。改訂3):

23. **台紙は A4 縦・2列×5行(10枠)を暫定採用**する(§4-2)。シールの重複防止と判読性を優先し、枠の間に余白を確保する。線は薄いグレー、各枠に日付の手書き欄を置く。**実物の試し刷りで貼付を確認してから最終決定**する(§9-1)。

25. **PDF はブラウザの印刷・PDF に保存の方式**とする。PDF のライブラリは原則追加しない。
26. **写真のディーラー閲覧の許可は独立した `stickerPhotoGrants`** で管理し、受注閲覧の権限(`dealerPortalGrants`)に影響させない(§8-3)。
27. 写真に患者氏名・ID を含めない方針、**EXIF など不要なメタデータの除去**、施設間のアクセスの分離を維持する(§8-2)。
28. **OCR は今回実装しない**。原本を保存しておき、将来対応できる構成とする(§7)。

## 1. 目的と前提

- 白内障手術後、手術室(3階)の眼科カートに掲示した IOL シールの台紙を、医師が外来へ運ばなくてよくする。手術室の看護師が台紙を個人のスマートフォンで撮影して送り、医療機関と、施設が許可したディーラーが閲覧する。
- 台紙には患者氏名・ID などの個人情報はない(撮影時にも写し込まない。§3 の ⓘ と QR シールの注意書きで徹底する)。
- 画質の優先: 手書きの大きな「×」と、シールの小さな文字(型番・度数・シリアル)が拡大して読めること。
- 看護師の操作は最小限。Google ログインは不要で、施設専用の QR コード(入口)と、別途共有されたアクセスコード(数字6桁以上)で送信を許可する。
- 写真は原則としてスマートフォンの写真ライブラリに残さない。
- 画面は既存の IOL Order と同じ見た目(白背景・カード・補助ボタン 36px・ⓘ・説明文の常時表示なし)。

## 2. 全体像

```
既存の台紙(使い方は従来どおり)       看護師のスマホ(sticker.html)              保存(施設ごと・サーバー専用)        閲覧
┌────────────────────┐  QR 読取  ┌───────────────────────┐  送信  ┌────────────────────┐  ┌─ 医療機関: 注文画面の関連リンク「IOLシール写真」
│ シールを貼る / ×を書く  │ ───────▶│ ①コード入力(毎回)          │ ─────▶│ 専用バケット: 画像     │─▶│   施設の所属者全員
│ [QRシール]を貼り足すだけ │         │ ②撮影 → ③確認 → ④完了     │        │ Firestore: 送信日時など │  └─ ディーラー: dealer.html のメニュー「シール写真」
└────────────────────┘         └───────────────────────┘        └────────────────────┘      施設が共有を許可した会社の担当者だけ
```

- 入口は `sticker.html`(`dealer.html` と同じく注文画面とは別の入口。ヘッダーは共通の見た目で、見出しは「IOLシール写真」、施設名はコードの確認後にだけ出す)。
- QR の中身は撮影ページの URL `https://iol.medconf.jp/sticker.html#f=<施設の入口トークン>` だけ。施設 ID もアクセスコードも含めない(トークンは施設設定で発行する不透明な値。§8-1)。QR コードは施設設定「IOLシール写真」から表示・印刷する(☰メニューには項目を足さない。§4)。
- 1枚の写真 = 1件の記録。1回のコードの確認から「終了」までを **撮影セッション**(1件の送信のまとまり)とし、枚数の固定上限は設けない(台紙が3枚以上でも、台紙1枚を分けて撮っても、「続けて撮影」で続けて送る)。同じセッションの中ではコードを再入力しない。閲覧画面ではセッション単位にまとめて表示する(§5)。

## 3. 看護師用(sticker.html。スマートフォン専用の見た目。PC でも動く)

### 3-1. 操作フロー

```
QR 読取 ─▶ [コード入力](毎回) ─▶ [撮影](開くとすぐカメラ) ─▶ シャッター ─▶ [確認](ピンぼけの疑いがあれば警告) ─▶ 送信 ─▶ [完了] ─▶ 続けて撮影 / 終了
```

- コードの確認 = **撮影セッション**の開始。その画面を開いている間(ブラウザのタブのメモリ。最長 30 分。送信のたびに延長はしない)だけ有効で、タブを閉じる・「終了」を押す・30分経つと、次は再入力(新しいセッション)。端末には何も保存しない。未送信の写真は、30分を過ぎても画面のメモリに残し、コードの再入力の後に同じアップロードIDで送る(§3-4・§8-2)。
- セッションの枚数に固定の上限は設けない(1週間分の台紙が3枚以上でも続けて送れる)。不正利用を防ぐ安全上限(1セッション 100 枚など。§8-2)に達したときだけ「送信の上限に達しました。時間をおいてお試しください」と止める。
- 30分を超えて続ける必要があるとき(まれ)は、コードを入れ直すと新しいセッションになる(閲覧画面では別のまとまりになるが、同じ日の見出しの下に並ぶ)。
- 撮影した写真は、送信が終わるまで画面のメモリにだけ置く。端末への保存・共有・ダウンロードの操作は置かない。

### 3-2. ① コード入力

```
┌──────────────────────────┐
│ IOLシール写真                     │  ← 共通のヘッダー(施設名はまだ出さない)
├──────────────────────────┤
│  アクセスコード                 ⓘ │
│  ┌────────────────────┐   │
│  │ ● ● ● ● ● ●           │   │  ← 半角数字(inputmode=numeric、autocomplete=one-time-code は使わない)。6桁以上
│  └────────────────────┘   │
│  [        次へ        ](主要ボタン)  │
│  コードが違います(必要なときだけ赤字)  │
└──────────────────────────┘
```

- ⓘ: 「施設から共有されたアクセスコードを入力してください。コードは施設の管理者・副管理者が設定・変更します。患者情報が写らないように撮影してください。」
- 連続して間違えたときは一定時間受け付けない(「しばらくしてからお試しください」。回数・残り時間は表示しない)。
- QR なしで `sticker.html` を開いた(トークンがない・無効な)場合は「台紙のQRコードを読み取って開いてください」とだけ表示する(施設名は出さない)。
- 確認が通ると、ヘッダーの下に施設名と **前回の送信の情報**(控えめな小さい文字)を出し(送り先と前回の送信の確認)、② へ。
  ```
  ○○眼科
  最終送信 11/4(火) 10:35 ・ 11月4日の手術分まで     ← 前回の最終手術日があるとき
  最終送信 11/4(火) 10:35                            ← 前回の最終手術日が未入力のとき(送信日時だけ)
  送信履歴なし                                       ← 送信履歴がないとき
  ```
  - 灰色・小さめ。説明文・「何日前」などの相対表示は付けない(狭い画面では「・」の後を次の行に折り返してよい)。
  - 値は `verify` の応答(§8-1)。**前回** = サーバーへの保存が正常に完了した最新の写真(削除した写真は除く)。送信日時はその写真の保存時刻(日本時間)。最終手術日はその写真が属する撮影セッションの値(未入力ならその部分を出さない。それより前のセッションの日付は持ち出さない)。今年以外は年も付ける(「2025/12/26(金) 16:10」「2025年12月26日の手術分まで」)。
  - 確認の前(コード入力の画面・QR なしの案内)には出さない。表示しても撮影・送信は制限しない(注意の色・確認のダイアログも出さない)。
  - 看護師の画面では、日時だけを出す。過去の画像・枚数・注文の情報は出さない。

### 3-3. ② 撮影

```
┌──────────────────────────┐
│ ○○眼科                      ⓘ │
│ 最終送信 11/4(火) 10:35 ・ 11月4日の手術分まで │  ← 控えめに(§3-2)。このセッションで送ると、その写真の日時とこのセッションの最終手術日に更新
├──────────────────────────┤
│ ┌──────────────────────┐ │
│ │     カメラ映像(縦いっぱい)     │ │  ← 四隅に薄いガイド(台紙を枠に収める目安)
│ └──────────────────────┘ │
│            ( ◯ ) 大きなシャッター   │
│  [ライトを点ける](対応端末だけ・補助)  │
└──────────────────────────┘
```

- 開いたらすぐ背面カメラを起動(`getUserMedia`。背面カメラと 4096×3072 を要求する。これは上限の希望で、端末が返す実際の解像度で撮る。向きも端末のまま。例: Galaxy S24 Ultra は 3060×4080)。写真ライブラリを経由しないので端末に残らない。
- カメラを使えない端末・許可されなかったときは「カメラを起動できません」+ [カメラで撮影](ファイル選択 `capture="environment"`)に切り替える(この経路は端末により写真が残ることがあるため、ⓘ にその旨を書く)。
- **端末差**(決定 §0-22): 取得した映像の長辺が **3000px 未満**(暫定。iPhone の検証で確定)のときは、確認画面に「この端末では解像度が低い可能性があります。文字が読めるか拡大して確認してください」と注意を出し、[カメラで撮影](ファイル選択)も選べるようにする。送信は止めない。実際の解像度は写真の記録(`width`・`height`)に残る。
- ⓘ: 「台紙全体が枠に入るように、真上から撮ってください。文字が読めるよう明るい場所で。患者情報が写らないようにしてください。」

### 3-4. ③ 確認

```
┌──────────────────────────┐
│ ┌──────────────────────┐ │
│ │   撮影した画像(ピンチで拡大)   │ │
│ └──────────────────────┘ │
│ ⚠ ピンぼけの疑いがあります。文字が   │  ← 判定したときだけ(黄色の注意)
│   読めるか拡大して確認してください  │
│  今回の最終手術日(任意)  [ 月/日  ] │  ← セッションの最初の送信の前だけ入力欄。既定は空(自動で入れない)。未来の日付は選べない
│  [ 撮り直す ]      [   送信   ]     │  ← 送信は主要ボタン。警告があっても・最終手術日が空でも送れる
└──────────────────────────┘

(同じセッションの2枚目以降の確認)
│  今回の最終手術日  11/4              │  ← 値を表示するだけ(再入力・変更はできない)。未入力で始めたセッションは「今回の最終手術日 未入力」
```

- **今回の最終手術日**(決定 §0-18): 台紙のどの日付(手術日)の分まで撮ったかの目安。任意で、既定は空(今日などを自動で入れない)。入力は日付の欄(R07 の注文日の欄と同じ部品。画面は「11/4」、今年以外は年も。押すと日付の選択)。未入力でも送信できる。
  - 撮影セッション全体で共通(決定 §0-20)。**最初の写真の送信の前に設定**し、最初の送信が成功した時点でセッションの値として決まる(未入力のまま送れば「未入力」で決まる)。2枚目以降の確認では値を表示するだけで、セッションの間は変更・追加の入力はできない。
  - 違う日付にしたいとき(入力の誤りなど)は「終了」して QR から開き直す(新しいセッションになる)。送信済みの写真の日付をまとめて付け直す処理は初期実装では作らない(誤りは閲覧の画面で写真の時刻から判断でき、必要なら医療機関が削除して送り直してもらう)。
  - 最初の送信が失敗して再送する間は、まだ決まっていないので欄を直してよい(再送の写真に付ける値も直した値になる。アップロードIDは同じ。すでに保存されていた場合はサーバーの値が返り、表示もそれにそろう)。
  - 入力できる範囲: **未来の日付(日本時間の明日以降)だけ不可**(決定 §0-19)。過去の日付は制限しない。日付の選択でも未来の日は選べない(`max` = 今日)。手で入力した未来の日付は「未来の日付は選べません」と出し、送信の前に欄を直してもらう(欄を空にすれば送れる)。
  - ⓘ(確認画面の ⓘ に1行): 「今回の最終手術日は、台紙のどの手術日の分まで撮ったかの目安です(任意)。」

- ピンぼけの判定: 画像を縮小してグレースケールにし、ラプラシアンの分散で鮮鋭度を測る(既存の `src/domain/image-sharpness.js`。しきい値は実機で調整)。警告を出したかどうかを `X-Blur-Warned` で送り、参考情報として記録する(§8-2)。
- 送る画像: **撮影した解像度のまま JPEG**(縮小なし・品質 0.92。決定 §0-21)。映像の1コマを同じ大きさのキャンバスに描いて JPEG にするため、EXIF は含まれない。ファイル選択の経路も、送信の前に同じ解像度のまま描き直して EXIF を落とす(§8-2)。送信前に画面上で容量を見せる必要はない。
- 送信中は [送信] を「送信中…」にして二重送信を防ぐ。失敗したら画像は残したまま「送信できませんでした。通信状態を確認して、もう一度お試しください」+ [再送信]。
- **チケットの期限切れ**: 送信がチケットの期限切れ(401)で失敗したら、写真と最終手術日の値を画面のメモリに残したままコード入力へ戻し、確認が通ると同じアップロードIDで自動で再送する(新しいセッションになる。すでに保存済みなら重複を作らず既存の記録が返る)。「終了」を押す・タブを閉じると写真は消える。

### 3-5. ④ 完了

```
┌──────────────────────────┐
│          ✓ 送信しました            │
│       11/4(火) 10:32  この回 3枚目    │  ← このセッションで送った枚数(重複は数えない)
│  [   続けて撮影   ](主要ボタン)     │
│  [ 終了 ](補助)                    │
└──────────────────────────┘
```

- 送信に成功すると、最終送信の表示をこの写真のサーバーの保存時刻とこのセッションの最終手術日に更新する(`stickerPhotoUpload` の応答。重複の再送〔`created: false`〕では変えない)。連続送信では最後の写真が基準になる。
- 「続けて撮影」で ②(カメラは起動したまま。コードの再入力なし。何枚でも続けられる)。「終了」で入口の案内に戻し、セッション(コードの確認)と画像を画面のメモリから消す。
- 送信済みの写真の一覧・削除は看護師の画面には置かない。誤送信は医療機関側で削除する(§5)。

## 4. 施設設定「IOLシール写真」(所属者全員に表示。変更の操作は施設管理者・副管理者)

**役割ごとの表示(決定 §0-43)**: 管理者・副管理者は、従来の施設設定の中の1セクションとして、以下のすべてを使う。注文者・代理入力者は、メニュー「施設設定」(この欄を使える施設だけに出る)から、**この欄だけの画面**を開く(`src/ui/sticker-settings-view.js`。担当医・採用 IOL などのほかの項目は読み込みも表示もしない)。出すのは、アクセスコードの状態(設定済み・未設定と変更日)、「QRコードを表示」「台紙を印刷」「QRコードのみ印刷」だけで、「設定/変更」「QRコードを作り直す」「ディーラーへの共有」は出さない。QR コードが未発行のときは、表示・印刷の操作も出さず、「施設の管理者・副管理者に発行を依頼してください」と案内する。コードの確認の停止中は「施設の管理者・副管理者にお知らせください」と案内する。

既存の施設設定の1セクション(「ディーラー画面での閲覧」の次。折りたたみ・ⓘ・自動保存の流儀は他のセクションと同じ)。アクセスコード・QR コード・ディーラーへの写真の共有を、このセクションにまとめる(決定 §0-15。☰メニューには項目を足さない)。

```
IOLシール写真 ▲ ⓘ
  アクセスコード
    設定済み(2026/11/03)                  [変更]
  QRコード ⓘ                              [表示]   ← 印刷はモーダルの中(§4-1)
                  (ⓘ の中: 説明と [QRコードを作り直す]。管理者・副管理者だけ。確認ダイアログ)
  ディーラーへの共有
                  ☐ ○○メディカル(発注先: ○○メディカル 東京)    ← 運営者が関連付けた発注先だけ。チェックで共有・外すと取消(自動保存)
                  ☑ △△商事
```

- **アクセスコード**: 未設定なら「未設定」+[設定]。設定後は「設定済み」と変更日だけを表示し、コードは再表示しない(決定 §0-8)。[変更] で半角数字6桁以上を入力 / [自動で作る] → [変更する](確認ダイアログ)。変更後はその画面に1回だけ新しいコードを表示し、看護師へ共有する案内を出す(閉じると再表示しない)。変更はすぐ有効。
- **QRコード**: 施設に入口トークンがまだなければ、最初に [表示] を押したときにサーバーが発行する(§8-1)。ボタンは補助ボタンの大きさ(36px)。[QRコードを作り直す] は、印刷した古い QR を無効にしたいとき(紛失など)だけ使う(確認ダイアログ:「これまでに印刷・貼付したQRコードは使えなくなります。新しいQRコードを印刷して貼り替えてください」)。
- **ディーラーへの共有**: 運営者が会社に関連付けた発注先(`dealerPortalLinks` に `companyId` がある。`status` は問わない)ごとにチェック。受注一覧の閲覧の許可(「ディーラー画面での閲覧」)とは別で、どちらか一方だけでもよい。関連付けがなければ「共有できるディーラーはありません」とだけ表示する(理由は ⓘ)。チェックを入れた時点以降に送られた写真だけが共有される。許可は `stickerPhotoGrants` に記録する(§8-3)。
- ⓘ: 「看護師が台紙を撮影して送るための設定です。アクセスコードは台紙やQRコードには載らず、設定後に再表示もできません。看護師へは別途お伝えください。忘れた場合は新しいコードに変更してください。ディーラーへの共有は、チェックを入れた後に送られた写真が対象です。」
- 「送信の受け付け」の一時停止・保存期間は第2段階。

### 4-2. 台紙を印刷(A4 縦・2列×5行。暫定。決定 §0-23〜25)

[台紙を印刷] を押すと、印刷の画面(見本・上部の表示の編集・発注先の選択・[印刷する])を開く。画面の部品は R07 の帳票と同じ流儀。

```
┌──────────────────────────────────────────┐  A4 縦(様式の中で 12mm の余白を取る。用紙の余白の指定は 0)
│ IOLシール貼付台紙                         ┌──────┐ │
│ 立川病院 眼科 → 栗原医療器械店 立川支店   │ [QR] │ │  ← 上部の表示(下記)。QR は約 28mm 角
│                                          └──────┘ │
├────┬──────────────┬─┬────┬──────────────┤
│ ／ │                          │ │ ／ │                          │  ← 左右2列 × 5行 = 10枠
│    │     シール貼付枠           │ │    │     シール貼付枠           │     列の幅 90mm・列の間 6mm
├────┼──────────────┤ ├────┼──────────────┤     日付欄 14mm + 貼付枠 76mm
│ ／ │                          │ │ ／ │                          │     行の高さ 約 46mm
│    │                          │ │    │                          │
├────┼──────────────┤ ├────┼──────────────┤  ← 区切り線は薄いグレーの細線
│ …  │                          │ │ …  │                          │
├────┴──────────────┴─┴────┴──────────────┤
│ 挿入できなかったレンズのシールには大きく×を書いて貼る ・ 患者氏名・IDは書かない (小さく) │
└──────────────────────────────────────────┘
```

- **枠の大きさ**: 印刷範囲 186×273mm。貼付枠は 76×約 46mm。枠の内側に 5mm ずつ空けると、貼れるシールの目安は **66×36mm まで**で、中央に貼ればシールとシールの間は約 10mm 空く(目安 5〜10mm を満たす)。メーカーごとの寸法の差は、最大のシールが収まる枠にして吸収し、メーカー別の様式は作らない。
- **暫定の扱い**: 行数はコードの1つの定数にする。実物の試し刷り(§9-1)で最大のシールが収まらないときは行数を減らし、余裕があれば増やすことを検討する。
- **日付欄**: 各枠の左に手書きの「／」(12pt 相当)。看護師が手術日を書く。
- **線**: 区切り線は薄いグレー(約 0.2mm。`#999` 相当)。シール・文字・バーコードの読み取りを妨げないよう、枠の中には何も印刷しない。塗りは使わない。白黒のプリンターで線がかすれないかも試し刷りで確かめる。
- **上部の表示**(決定 §0-24): 1行の文字列「施設名 診療科 → 発注先」。14pt の題名の下に 11pt で出す。長いときは2行に折り返す。
  - 初期値(自動入力): 施設名は施設の `name`。発注先は `facilityDealers` の `mailName`、なければ `name`。**診療科と支店名の専用の項目はない**ので、登録された文字に含まれていなければ出ない(新しい項目を追加しない)。
  - 発注先が1社なら自動で入れ、2社以上なら印刷の画面の選択で選ぶ。0社なら「→」以降を出さない。
  - 編集: 印刷の画面の1行の入力欄で直せる(最大 100 文字。文字は `textContent` で扱う)。**編集した内容は保存せず、画面を閉じると初期値に戻る**。施設・発注先の設定には書き戻さないため、注文メールの宛名(`mailName`)などは変わらない。
  - 発注先の表示は**案内のためだけ**で、写真の閲覧の権限には使わない(閲覧は §8-3 の `stickerPhotoGrants`)。QR は施設で1つなので、台紙の発注先を変えても写真の送り先は変わらない。
- 上部の QR は施設専用の入口(`getEntryQr`)。印刷日・アクセスコード・URL の文字列は載せない。
- **印刷・PDF**(決定 §0-25): `@media print`(R07 の帳票と同じ方式)で、台紙の画面を開いている間だけ台紙を A4 に出す。[印刷する] はブラウザの印刷を開き、印刷先に「PDF に保存」を選べば PDF になる。拡大縮小は 100%。PDF のライブラリは追加しない。

## 8. 技術設計(認証・画像の保存・閲覧の権限)

Functions・Rules・写真専用バケットはいずれも新規の領域に閉じ、注文の受付・メール・ディーラー受注一覧の処理には組み込まない(既存の処理は変更しない)。既存の機能スイッチとは別に `STICKER_PHOTO_ENABLED`(既定 false)と、第1段階で有効にする施設の一覧 `STICKER_PHOTO_FACILITY_IDS` を設ける。

**関数の構成**(決定 §0-34)。認証の方式ごとに関数を分け、ログインなしで呼べる処理を2つに限る:

| 関数 | 種類 | 認証 | 処理 |
| --- | --- | --- | --- |
| `stickerEntryApi` | callable | なし(入口トークン + アクセスコード) | `verify` だけ |
| `stickerPhotoUpload` | HTTP(PUT) | 送信チケット | 写真の保存だけ |
| `stickerPhotoApi` | callable | **Firebase Auth 必須**(すべての処理の先頭で確認) | `list`・`dealerList`・`delete`・`getSettings`・`setAccessCode`・`getEntryQr`・`rotateEntryQr`・`setDealerShare` |
| `stickerPhotoImage` | HTTP(GET) | **Firebase Auth の ID トークン必須** | 画像の読み出しだけ |
| `stickerPhotoCleanup` | スケジュール(1日1回) | 外部から呼べない | 孤立ファイルと、期限切れの回数制限の記録の片付け |

### 8-1. 入口トークンとアクセスコード(看護師の送信の認可)

- **入口トークン**(QR の `#f=`): 施設設定で初めて QR を表示するときにサーバーが発行する 128 ビットの乱数(URL 安全な文字列)。`stickerEntries/{token}` → `{ facilityId, status: active|revoked, createdAt }` に保存し、施設側の参照は `facilities/{fid}/stickerSettings/entry` の `{ token, updatedAt }` に持つ(施設の文書には足さない)。トークンだけでは何もできない(コードが必須)。
- **QR の API**(`stickerPhotoApi`。管理者・副管理者。決定 §0-33): `getEntryQr { facilityId }` は入口トークンがなければ発行し、撮影ページの URL(`https://iol.medconf.jp/sticker.html#f=<トークン>`)だけを符号化した SVG を返す。`rotateEntryQr { facilityId }` は旧トークンを `revoked` にして新しいトークンを発行し、同じ形で SVG を返す(「QRコードを作り直す」。印刷済みの古い QR を無効にできる。発行済みのチケットは期限まで有効)。「サイトを共有」と同じ設定(qrcode 1.5.4)。画面はこの SVG をモーダル・2種類の印刷に使う。トークンは画面に文字として表示しない。
- **アクセスコード**: 半角数字6桁以上、上限 12 桁。`facilities/{fid}/stickerSettings/access` に `{ algo, salt, hash, codeGeneration, updatedAt, updatedBy }` を保存し、平文は保存しない。ハッシュは Node.js 標準の `crypto.scrypt`(コードが短いため salt + 高いコスト。依存パッケージを増やさない)で、比較は `timingSafeEqual`。決定 §0-8 のとおり、`getSettings` は「設定済み」と変更日だけを返し、再表示の API は作らない(忘れたら変更する運用)。`setAccessCode` は `codeGeneration` を1増やす。
- **確認の流れ**(callable `stickerEntryApi`。ログインなし。App Check は導入後に必須にする):
  1. `verify { token, code }` → トークンが active・コードのハッシュが一致なら、**送信チケット**(サーバー署名の HMAC トークン。`STICKER_TICKET_SECRET` で署名。中身: 施設 ID・セッション ID・コードの世代・発行時刻・有効期限 30 分・乱数)と施設名、**前回の送信の情報** `lastSentAt`(ISO。なければ null)と `lastSurgeryDate`(YYYY-MM-DD。その写真のセッションで未入力なら null)を返す。チケットはタブのメモリにだけ置く。失敗の応答には施設名・最終送信日時を含めない。
     - `lastSentAt` = その施設の写真のうち、**保存が正常に完了した**(`status: "stored"`。削除した写真は除く)最新の `takenAt`。`lastSurgeryDate` = その同じ写真の `lastSurgeryDate`(セッションの値)。`stickerPhotos` を `status`・`takenAt` の降順で1件だけ読む(複合インデックスを1つ追加)。画像・枚数・ID は返さない。
     - アップロードの応答(`stickerPhotoUpload`)にも、その写真の `takenAt` と `lastSurgeryDate` を含める(画面の表示の更新用)。
  2. 失敗はトークンの有無・コードの違いを区別しない同じ応答。**回数制限**: 失敗の回数を、トークンごとに 10 回/10 分、送信元 IP ごとに 30 回/10 分で数え、超えたら 15 分停止する。記録は専用の `stickerRateLimits/{SHA-256(種類 + 値)}` に置く(既存の `rateLimits` は uid 単位のため変更しない。IP はハッシュだけ)。これだけでは、10 分に 10 回までの低速の総当たり(1 日 1,440 回)が止まらないので、**入口トークンごとに 24 時間で 50 回**の失敗の上限を足す(超えたら 24 時間停止。決定 §0-38・§8-6)。6桁でも総当たりには数十年かかる。コードを変えると、旧コードでの確認は以後失敗し、発行済みのチケットも世代の不一致で拒否する。 回数は**確認の前に確保**し、成功したら返す(同時に送っても上限を超えて試せない)。トークンが無効なときも同じ読み取りとコードの計算を行い、応答と処理の差を抑える。機能の停止中も同じ応答。
- 監査: `verify` の成功・停止(停止の範囲〔送信元・トークンの短い窓・24 時間〕、トークンのハッシュ、その時点の失敗の数)、24 時間の窓ごとの失敗の数(`verify.daySummary`)、コードの変更、QR の作り直し、ディーラーへの共有の変更、写真の削除を `stickerAuditLogs` に記録(IP は保存せずハッシュのみ)。写真の保存は `stickerPhotos` の記録で足りる。

### 8-2. 画像の保存(専用の GCS バケット)

- バケットは写真専用に新設する(`medconf-iol-dev-sticker-photos`。同じプロジェクト内。別のプロジェクトは作らない)。Firebase Storage には連携せず、GCS のバケットと IAM で管理する(決定 §0-36)。クライアントには権限がないため、読み書きは Functions を通すしかない。パスは `{facilityId}/{photoId}_{試行のID}.jpg`。試行のIDは送信の試行ごとの乱数で、同時の送信が互いのオブジェクトを上書き・削除しない(記録が指すのは1つの試行のオブジェクトだけ)。サムネイル(長辺 400px)は同じ名前に `_thumb` を付けたパスに Functions が作る(一覧の読み込みを軽くする。原本は触らない)。
- **送受信の経路: A 案(Functions がプロキシ)を採用**(決定 §0-10。B 案は比較のために残す)。権限の確認・アクセスコードの認証・送信チケットの検証はすべてサーバー(Functions)で行い、ブラウザの判定は表示の補助にすぎない。
  - **A 案(採用): Functions がプロキシ**。アップロードは HTTP 関数 `stickerPhotoUpload`(onRequest)に、ブラウザが画像のバイト列をそのまま PUT する(ヘッダーにチケット・アップロードID・SHA-256)。関数が検証してから自分の資格情報でバケットに書く。閲覧も HTTP 関数 `stickerPhotoImage`(onRequest)が、所属・許可を確認してからバケットから読み出して返す(`Cache-Control: private, no-store`。許可の取消をすぐ反映するため)。**署名付き URL を使わないので `iam.serviceAccountTokenCreator` は不要**。必要なのはバケットへのオブジェクトの読み書き・削除だけ。関数の帯域と実行時間を使うが、量(§8-2 末尾)からみて問題ない。
  - **Functions(第2世代 = Cloud Run)の容量の制限(確認)**: HTTP 関数のリクエスト本文は **32MiB** まで、レスポンスも **32MiB** まで(ストリーミングでなければ)。画像の上限 15MB(§下)はどちらにも収まる。callable(`onCall`)はこの経路に使わない(JSON で base64 にすると 1.33 倍になり、メタデータ以外には向かない)。タイムアウトは `stickerPhotoUpload` を 300 秒、`stickerPhotoImage` を 60 秒に設定(既定 60 秒では遅い回線の 15MB の受信が切れうる)。メモリはサムネイル作成(`sharp`)のため 1GiB。同時実行は `maxInstances` 10・`concurrency` 1(画像処理のメモリを分けない)。**ウォームアップは行わない**(決定 §0-35。`verify` と `stickerPhotoUpload` は別の関数で、一方を呼んでも他方は起動しない。`minInstances` も設定しない)。送信の最初の1枚が数秒遅いことがあるが、画面は「送信中…」のまま待つ。実際の時間は §9-1 の検証で確かめる。
  - **B 案: 署名付き URL(V4)**。callable が PUT 用・GET 用の短時間の URL を返し、ブラウザがバケットと直接やり取りする。関数の負荷は小さいが、実行サービスアカウントに自分自身への `iam.serviceAccountTokenCreator`(署名)が必要で、バケットに CORS の設定が要る。
- **CORS**(決定 §0-29): HTTP 関数が応答する。バケット側の CORS 設定は不要。

  | 関数 | `Access-Control-Allow-Methods` | `Access-Control-Allow-Headers` |
  | --- | --- | --- |
  | `stickerPhotoUpload` | `PUT, OPTIONS` | `Content-Type, X-Sticker-Ticket, X-Upload-Id, X-Content-Sha256, X-Last-Surgery-Date, X-Blur-Warned` |
  | `stickerPhotoImage` | `GET, OPTIONS` | `Authorization, X-Dealer-Company, X-Dealer-Device`(後の2つはディーラーの担当者の確認) |

  - どちらも `Access-Control-Allow-Origin: https://iol.medconf.jp`(ほかのオリジンは拒否)・`Vary: Origin`・`Access-Control-Max-Age: 3600`。Cookie を使わないので `Access-Control-Allow-Credentials` は付けない。応答の項目は JSON の本文で返すので `Access-Control-Expose-Headers` も不要。
  - 上の表にないメソッドは 405。ローカルの検証でオリジン `http://127.0.0.1:*` を許可するのはエミュレータの設定だけ。callable(`stickerEntryApi`・`stickerPhotoApi`)の CORS は既存の callable と同じ。
- **ファイルサイズの制限**(多段):
  1. 上限は **ブラウザ側・サーバー側で同じ 15MB**(決定 §0-11。暫定。実機検証の後に見直す)。値は `src/domain/sticker-photo.js` と `functions/src/sticker-photo.js` の定数に置き、一致を unit テストで確かめる(画面の上限とサーバーの上限を同期している既存のテストと同じ方式)。
  2. ブラウザ: 送信前に JPEG の大きさを確認し、15MB を超えるときは送らず「画像が大きすぎます。もう一度撮影してください」(Galaxy S24 Ultra の 3060×4080 で実測 約 1.7MB。シールの多い台紙では大きくなる見込みのため、上限は 15MB のまま維持する)。ブラウザの確認は利用者への案内のためで、認可・制限の判定ではない。
  3. HTTP 関数(こちらが本当の制限): `Content-Length` がない・15MB を超えるときは本文を読まずに 413。先頭のバイト列が JPEG(`FF D8 FF`)でないとき・JPEG のヘッダーから幅と高さを読めないとき・1億画素を超えるときは 415。実際に受け取ったバイト数が宣言と違う・SHA-256 がヘッダーの値と一致しないときは保存せず 400(受信内容の検証)。
  4. 件数の**安全上限**(運用上の枚数制限ではなく、不正利用を止めるための値。設定で変えられる): 1セッション(30分)あたり **100 枚**、施設あたり 1 日 **300 枚**・**3GB**。超えたら 429 で「送信の上限に達しました。時間をおいてお試しください」(どの上限かは画面に出さない)。通常の利用(1週間に台紙2〜3枚を数枚に分けて撮る)では届かない。管理の方法は下の「送信枚数・容量の管理」。
  5. バケット: オブジェクトのライフサイクルは第3段階(保存期間)まで設定しない。
- **不要なメタデータの除去**(決定 §0-27。画素は変えない):
  1. ブラウザ: 映像の1コマはキャンバスから作るので EXIF を含まない。ファイル選択の経路は、向きを反映して同じ解像度のまま描き直してから送る。
  2. サーバー(こちらが本当の処理): 受信した JPEG のセグメントを終わり(EOI)まで読み、復号の表と、表示に必要なもの(サムネイルのない APP0 の JFIF・APP2 の ICC・APP14 の Adobe)以外のセグメント(Exif・XMP・IPTC・MPF・JFIF のサムネイル・未知のセグメントなど)とコメント(COM)、EOI より後のデータを取り除いてから保存する。プログレッシブのスキャンの間のセグメントも同じ扱い。バイト列の操作だけで、再圧縮はしない。ライブラリは追加しない。
  3. `X-Content-Sha256` は受信内容の検証に使う値で、除去の前のバイト列と比べる。同じ内容の再送は同じ結果になるので、次の項目の重複防止は変わらない。
  4. 位置情報・端末の情報は保存しない。写真に写り込んだ患者情報は機械では除けないので、画面の ⓘ と台紙の注意書きで防ぐ(誤送信は §5 の削除)。
- **送信途中の失敗・再送時の重複防止**(**撮影ごとに固定のアップロードID** を基本とする。決定 §0-12・§0-30):
  1. ブラウザは **撮影した写真ごとに1回だけ** アップロードID(`crypto.randomUUID()`。UUID v4)を作り、画像と一緒に画面のメモリに持つ。自動の再送・[再送信]・チケットの期限切れの後のコードの再入力を経ても、その写真ではずっと同じIDを使う(`X-Upload-Id`)。「撮り直す」で新しい写真になったら新しいID。あわせて画像の SHA-256 を計算して送る。
  2. サーバーは `photoId = SHA-256(facilityId + ":" + uploadId)` で決める。**チケットとセッションを含めない**ので、再認証の後の再送も同じ `photoId` になる。施設を含むので、別の施設の写真とは衝突しない。形式が UUID v4 でないIDは 400。
  3. 保存の順序: (a) チケットと本文を検証する → (b) `photoId` の記録があれば、バケットに書かず既存の記録を返して 200(`created: false`)。SHA-256 が記録と違うときは 409(既存の写真を上書きしない)。削除済みの写真は復元しない → (c) 上限を事前に確認する → (d) メタデータを除去し、この試行だけの名前でバケットに保存する → (e) トランザクションで記録を登録する(下の「送信枚数・容量の管理」)。同じ写真の同時送信でも登録は1件だけで、登録できなかった試行(再送・内容の違い・上限・確認の後の削除)は**自分のオブジェクトだけ**を消す → (f) サムネイルを作り、まだ保存済みなら記録に付ける(作る間に削除されたら消す)。
  4. **SHA-256 は受信内容の検証と記録にだけ使う**。IDが違う送信は、画像が同じ内容でも別の写真として保存する(看護師が意図して同じ台紙をもう一度送る場合もあるため、内容の一致だけで自動的に除外しない)。
  5. 本文の受信が途中で切れたとき(`Content-Length` に満たない)は保存せず 400。ブラウザは自動で最大 3 回(1・2・4 秒後)再送し、それでも失敗したら [再送信] を出す(画像は画面のメモリに残す)。チケットの期限切れ(401)は §3-4 のとおりコードの再入力へ進む。
  6. 保存に成功したのに応答がブラウザに届かなかった場合も、再送(再認証の後を含む)が同じIDで既存の記録を返すので二重にならない。「送信しました」の枚数は、サーバーの応答の `created: true/false` で数える(重複は数えない)。タブを閉じると写真もIDも消えるので再送は起きず、もう一度撮れば別の写真になる。
  7. サムネイルの作成に失敗しても、写真の保存は成功として扱う(`thumbPath: null`)。`stickerPhotoImage` は `size=thumb` でサムネイルがなければ原本を返す。孤立したオブジェクト(記録のないもの)は `stickerPhotoCleanup` が1日後に削除する。
- **メタデータ** `facilities/{fid}/stickerPhotos/{photoId}`: `{ facilityId, uploadId, sessionId(撮影セッション = 送信チケットの ID), seq(セッション内の送信順), status: "stored"|"deleted", takenAt(サーバー時刻 = 送信日時), lastSurgeryDate(YYYY-MM-DD|null。セッションの今回の最終手術日), width, height(サーバーが JPEG のヘッダーから読む), bytes, sha256, blurWarned: bool, storagePath, thumbPath, deleted?: { at, by }, createdAt }`。患者情報・端末の識別子は持たない。Rules はクライアントの読み書きをすべて拒否し、読み取りは `list`・`dealerList` だけにする(決定 §0-37)。
- **`blurWarned`**(決定 §0-31): 画面は確認画面で警告を出したときだけ `X-Blur-Warned: 1` を送る。それ以外の値・ヘッダーなしは false。**クライアントの申告なので参考情報**として扱い、一覧の ⚠ と「ピンぼけの疑いで送信」の表示にだけ使う。認可・上限・削除の判定には使わず、サーバーで画像の判定はしない。
- **送信枚数・容量の管理**(決定 §0-32): `rateLimits` は使わず、次の2つの小さな文書で管理する(どちらも Rules で全拒否)。
  - `facilities/{fid}/stickerSessions/{sessionId}`: `{ count, lastSurgeryDate, createdAt }`
  - `facilities/{fid}/stickerUsage/{yyyymmdd}`(日本時間の日付): `{ photos, bytes }`
  - 写真の登録は1つのトランザクションで行う: `stickerPhotos/{photoId}`・セッション・当日の使用量を読み、記録があれば既存を返す(確認の後に削除された写真なら復元せず、保存したオブジェクトを消す)。同じIDで内容が違えば登録せず 409 にして、自分が保存したオブジェクトだけを削除する。上限(セッション 100 枚・1日 300 枚・3GB)を超えるなら登録せず 429 にして、保存したオブジェクトを削除する。超えなければ写真の記録を作り、`seq = count + 1`・`count`・`photos`・`bytes` を更新する。
  - Firestore のトランザクションの再試行により、同時に送っても上限を超えず、`seq` も重複しない。(c) の事前確認は無駄な保存を減らすためだけで、判定はトランザクションで行う。
  - 写真を削除しても数は戻さない(不正利用を止めるための値のため)。どちらの文書も小さいので、第3段階の保存期間まで残す。
- **セッションのまとまり**: 一覧(`list`)は写真を `takenAt` の降順で返し、画面が同じ `sessionId` を1つの枠にまとめる(枠の時刻の範囲・枚数・最終手術日は画面で計算。最終手術日はセッションの中で同じ値)。拡大表示の前後は同じ `sessionId` の `seq` 順。
- **今回の最終手術日の受け渡し**(決定 §0-18〜20): アップロードのヘッダー `X-Last-Surgery-Date`(任意。YYYY-MM-DD)で、画面が持つセッションの値を毎回送る。サーバーは形式と範囲(**日本時間の今日より後は不可**。過去は制限しない)を確かめ、形式違い・未来の日付は 400(画面は送る前に同じ確認をする)。
  - **セッションの値はサーバーが最初の写真で固定する**: 登録のトランザクションの中で、`stickerSessions` の文書があればその値を使い、ヘッダーの値が違っても新しい写真にはセッションの値を付ける(応答で返すので、画面の表示もそれにそろう)。文書がなければヘッダーの値(または null)をセッションの値として作る。
  - 送信済みの写真の値をまとめて付け直す API(`setSessionInfo` など)は初期実装では作らない(決定 §0-20)。
- **メタデータと画像の読み出し**(決定 §0-37): 一覧は `list { facilityId, from, to, cursor }`・`dealerList { companyId, deviceToken, facilityId, from, to, cursor }`(callable。最大 60 件/回。`dealerList` は `facilityId` を省くと閲覧できる施設だけを返す)で受け取る。権限の確認は関数の中の1か所で行い、返す項目を列挙する(`photoId`・`sessionId`・`seq`・`takenAt`・`lastSurgeryDate`・`width`・`height`・`blurWarned`。`storagePath`・`uploadId`・`sha256` は返さない)。サムネイル・原本は `stickerPhotoImage?facility=…&photo=…&size=thumb|full`(HTTP 関数。所属または共有の許可を毎回確認)から読む。`<img>` の `src` は認証のヘッダーを送れないので、画面が `fetch` に Firebase Auth の ID トークンのヘッダーを付けて取得し、Blob の URL を `<img>` に渡す(画面を閉じたら解放する)。URL をページの外へ持ち出さない(ダウンロード・共有ボタンは置かない)。
- **削除**(医療機関の管理者・副管理者): `delete { facilityId, photoId }` → Firestore に削除の記録を残し(`status: "deleted"`)、バケットの原本とサムネイルを削除する(復元なし。誤送信用)。
- 容量と料金の目安: 1枚 1.7MB(実測)〜5MB(シールの多い台紙の見込み)× 月 100 枚 ≈ 0.17〜0.5GB/月/施設。1年で 2〜6GB/施設。保存料は仮に $0.03/GB・月として 1年後でも月 $0.2 未満/施設(東京の単価は導入前に見積もりツールで確認する。Firebase の無料枠の対象は米国の一部のリージョンだけ)。保存期間を決めるまでは残す(第3段階で自動削除)。

  - 許可できるのは、運営者が会社に関連付けた発注先(`dealerPortalLinks` に `companyId` がある)だけ。関連付けの `status`(`active` は受注閲覧の許可中を表す)と `currentGrantId` は読まないので、受注閲覧の許可・取消は写真の共有に影響しない。受注一覧の許可がなくても写真だけ共有でき、逆も同じ。許可した時点の発注先の指紋の照合は受注の許可と同じ考え方で、関連付けの会社が変わった・発注先の識別項目が変わった許可は無効として扱う。

- 許可より前に送られた写真は返さない(`takenAt >= effectiveFrom`)。取消の後は一覧から消え、画像も読めなくなる(毎回確認する)。

**画像処理**: `stickerPhotoUpload` の中で順に行う: JPEG の検証・幅と高さの読み取り・メタデータの除去(§8-2)→ 保存 → `sharp` でサムネイルの作成。原本は再圧縮しない。

**Rules とインデックス**: Firestore Rules に、`stickerEntries`・`stickerPhotoGrants`・`stickerAuditLogs`・`stickerRateLimits`、施設の下の `stickerSettings`・`stickerPhotos`・`stickerSessions`・`stickerUsage` を、既存の流儀で明示的に全拒否として追加する。`firestore.indexes.json` に `stickerPhotos`(`status`・`takenAt` 降順)を追加する。バケットを Firebase に連携しないので、バケット用の Rules は作らない。

**テスト環境**: `firebase.json` は変更しない(`storage` の設定と、そのエミュレータは追加しない)。バケットの操作は小さな部品(`save`・`read`・`delete`・`list`)にまとめ、テストではメモリ上の偽物に差し替える。Firestore のトランザクションは既存の `test:functions`(Firestore エミュレータ)で確かめる。実際のバケットでの動作は配備の後に確認する(§9-3)。

### 8-6. 公開前のセキュリティレビュー(2026-11-05)と対応

対象は `feature/r09-integration`。Critical・High はなし。対応は次のとおり(決定 §0-38〜41)。

**(1) 入口トークンごとの 24 時間の失敗の上限(M-1)**
- 理由: QR(入口トークン)は秘密として扱えない(台紙の写真に写り、共有先のディーラーや退職者も知り得る)。短い窓の制限だけでは、10 分に 10 回までを続ける総当たりが止まらず、記録にも残らなかった。
- 実装: `stickerRateLimits/{SHA-256("tokenDay:" + トークン)}` に、最初の失敗から 24 時間の窓で失敗を数える(`STICKER_RATE_LIMITS.tokenDayMax` = 50・`dayWindowMs`・`dayBlockMs` = 24 時間)。短い窓と同じく、確認の前に確保し、成功したら返すので、正しい入力は数えない。超えると 24 時間、正しいコードも通らない(応答は短い窓の停止と同じで、理由を区別しない)。ほかの施設(別のトークン)には波及しない。
- 監査(`stickerAuditLogs`。コード・トークン・IP の平文は残さない): 停止したとき `verify.blocked`(`scopes`・`tokenHash`・`dayFailures`・`ipHash`)。24 時間の窓が終わったとき、その窓の失敗の数を `verify.daySummary`(`tokenHash`・`failures`・`windowStart`)として残す(次の確認のとき、または `stickerPhotoCleanup` が記録を消すとき)。`tokenHash` は `stickerEntries` の文書 ID(トークン)から計算して施設と対応づける。
- **復旧(管理者・副管理者。専用の解除の操作は作らない)**:
  1. 施設設定「IOLシール写真」に、停止中だけ案内(いつまで・復旧の方法)を出す(`getSettings` の `verifyBlockedUntil`・`verifyFailures24h`。今の QR のトークンの記録だけを読む)。撮影画面の停止の案内には「続くときは、施設の管理者にお知らせください」を足した。
  2. **アクセスコードを変更する**と、今の QR のトークンの制限(短い窓・24 時間)を同じトランザクションで消し、すぐに新しいコードで使える。コードが変わればそれまでの試行は手がかりにならないので、解除しても安全。解除は `code.change` の監査に残す(`limitsCleared`・`wasBlocked`・`clearedDayFailures`)。送信元 IP の制限は解除しない。
  3. 心当たりがない(誰かが試している)ときは、**QR も作り直す**。新しい QR は新しいトークンなので制限がなく、古い QR は無効になる(台紙・QR の刷り直しが要る)。
  4. 何もしなくても、24 時間で自動的に戻る。解除の後も制限は効く(新しいコードへの総当たりも 50 回で止まる)。
- 運用の目安: 看護師の打ち間違いは成功すると数えないので、通常の利用では上限に届かない。停止が起きたら、まず誤入力が続いた事情を確かめ、不明ならコードの変更と QR の作り直しの両方を行う。

**(2) `stickerEntryApi` の CORS(L-2)**
- `cors` を `https://iol.medconf.jp` だけにした(エミュレータ〔`demo-` のプロジェクト〕では `http://127.0.0.1:<port>` も)。撮影画面の要求(JSON の POST とその事前確認)は通る。`stickerPhotoUpload`・`stickerPhotoImage` は元から同じオリジンだけ。`stickerPhotoApi` はログイン必須の callable で、ほかの callable と同じ設定のまま(権限は毎回サーバーが確かめる)。
- CORS はブラウザが応答を読めるかの制限で、認可ではない。ブラウザ以外からの要求は CORS では止まらないので、コード・回数制限・チケット・ログインで止める。

**(3) 共有の許可の記録と、施設・発注先の一致(L-3)**
- `stickerPhotoGrants/{施設ID}_{発注先ID}` は、記録の ID に加えて、中の `facilityId`・`localDealerId` が一致するときだけ使う(一覧・画像・設定の表示・許可・取消)。一致しない記録が同じ ID にあるときは、読まず、取り消さず、上書きもしない(`failed-precondition`)。

**(4) 配備の後に確かめること: 送信元 IP の取り方(M-2)**
- `clientIpOf` は `X-Forwarded-For` の末尾を使う。実環境でこれが利用者ごとの値でなければ、送信元ごとの制限(10 分に 30 回)が全施設で共有されてしまう。
- 手順(機能スイッチが false のままでできる。確認の関数は停止中も同じ処理をするため): 別々の回線(例: Wi-Fi と携帯の回線)から、撮影ページで誤ったコードを1回ずつ送る → Firestore の `stickerRateLimits` で `scope` が `ip` の文書を見る。**文書が2つ(それぞれ `count` 1)なら正しい**。1つにまとまっていたら、取り方が誤っているので、機能を有効にせず `clientIpOf` を直す。IP そのものはログにも記録にも出さない(記録の ID はハッシュ)。
- あわせて、片方の回線で 31 回失敗させて停止させ、もう片方の回線からは確認できること(波及しないこと)を確かめる。

**(5) バケットの設定(M-3)**: Soft Delete 無効(0 日)・バージョニング無効(決定 §0-39)。削除は取り消せない。作成の後に設定を読み取って確かめる。

**(6) 配備の順序(M-4)**: §9-3。

**(7) 受容(L-4〜L-6)**: 決定 §0-41。コードは変更していない。


### 8-7. メニューを出す対象(試験運用。決定 §0-42)

- 公開の設定(`STICKER_VIEWER_ENABLED`・`STICKER_SETTINGS_ENABLED`)は全施設で共通の定数なので、これだけでは対象外の施設にもメニューが出る。そこで、設定が true のときも、**サーバーが「使える」と答えた対象だけ**にメニューを出す(`src/domain/sticker-photo-view.js` の `createStickerAvailability`)。
- **医療機関**: `stickerPhotoApi` の `status { facilityId }` が、所属していて機能と施設(`STICKER_PHOTO_FACILITY_IDS`)が有効なときだけ `{ enabled: true }` を返す。停止中・対象外・未所属は理由を区別せず `false`(エラーにしない)。画面は施設ごとに1回問い合わせ、**施設が変わったら確かめ直す**。答えが届くまで・確かめられないときは出さない。切り替えの前の施設への答えは捨てる。
- **ディーラー**: `dealerList`(施設の指定なし)が返す施設が1つ以上あるときだけ出す。会社に入るたびに確かめ直す。
- **関連リンクの「IOLシール写真」**(医療機関の入口。決定 §0-43): 上の問い合わせが `true` の施設だけに出す。関連リンクの読み込みとは別に切り替わり、施設を出ると消える。
- **施設設定の項目**: `getSettings` が拒否された施設では項目を隠す(従来どおり)。注文者・代理入力者のメニュー「施設設定」は、公開の設定が true で、上の問い合わせが `true` の施設だけに出す(`showSettingsMenu`)。管理者・副管理者には従来どおり常に出す。
- 表示だけの制御で、権限はこれまでどおり各処理がサーバーで毎回確かめる(メニューを出さない施設の利用者が直接呼んでも拒否される)。
- **機能の停止中の入口**: ログインなしで届く `stickerEntryApi`・`stickerPhotoUpload` と、`stickerPhotoImage`・`stickerPhotoApi` は、停止の間、正しいコード・チケット・所属があっても拒否し、写真を読み書きしない(応答の一覧と確認のコマンドは `docs/r09-deploy-runbook.md` 段階 5)。
- 配備の手順は `docs/r09-deploy-runbook.md`、立川病院の試験運用の手順は `docs/r09-pilot-guide.md`。

## 10. 将来のアイデア: OCR・バーコード認識によるディーラー別の写真表示(未実装)

**背景**: QRコードとアクセスコードは施設ごとに共通とし、看護師が送信先ディーラーを選択しない方針を維持する。一方、複数ディーラーを利用する施設では、他社が担当するIOLシールを必要に応じて非表示にしたい。

- 写真中の**個々のIOLシールの領域**を検出し、OCR・バーコード認識でメーカー・型番等を読み取る。ディーラーへの担当の対応付けは、メーカー名だけで決めつけず、施設側の取引先・採用品目等の設定を利用する。
- **担当外と確実に判別できたシール**は、該当ディーラー向けの画像でシール全体を黒く塗りつぶす。バーコード部分だけではメーカー名・型番・度数・シリアル番号が残るため不十分。
- **判別不能・認識に自信がないシールは表示する**。ユーザーの意向として、隠しすぎによる確認漏れ・取りこぼしを防ぐことを優先する。判別不能である旨を示す表示方法は将来検討する。
- 元の写真は施設側の保管庫に保持し、ディーラーには許可された施設の写真をもとに**サーバー側で加工した画像だけ**を配信する(ブラウザの黒いオーバーレイだけで隠さない)。
- 判別不能を表示する方式では他社のシールが見える可能性が残る。**このトレードオフは明示し、施設管理者がディーラーへの共有許可を管理する**。他社情報の非開示が必要な施設向けには、確認後に公開するなどの選択肢を将来検討する。

これは**将来の構想メモ**であり、R09第1段階の実装・段階構成・現行の共有許可の仕様を変更しない。OCRの精度やディーラー担当の判定方法を実物のシールと施設運用で検証してから採否を決める。
