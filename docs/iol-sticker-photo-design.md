# R09 使用済みIOLシール写真(台紙の撮影・送信・閲覧)設計

状態: **設計済み・実装待ち**(2026-11-03、Claude Code が起案し、同日ユーザーが基本方針を採用して §0 を決定。改訂2で実機検証・IAM・コードの表示・CORS/サイズ/重複防止を追記。実装・デプロイ・IAM の変更は未着手)。
OCR・文字抽出・Excel 出力は対象外(別の段階で検討)。

## 0. 決定事項(2026-11-03、ユーザー)

1. **ディーラーへの共有と閲覧は第1段階**に含める。今回の最重要目的は、医師が手術室から外来へ台紙を運ばなくても、ディーラーが写真を確認できること。
2. **アクセスコードは毎回入力**する(端末に記憶しない)。コードは**施設管理者・副管理者**が設定する**半角数字6桁以上**。
3. **撮影画像の圧縮条件(長辺 3000px など)は保留**。シールの細かな文字・シリアル番号の判読を優先し、実機検証の後に決める。それまでは撮影した解像度のまま送る前提で設計する。
4. **既存の台紙の使い方はなるべく変えない**。台紙に施設専用の **QR コードを貼る**だけで対応する。
5. **アクセスコードは台紙に記載・印刷しない**。台紙に貼るのは QR コードだけで、QR にもコードを含めない。QR・台紙の印刷画面にもコードを載せない。コードは施設管理者・副管理者が設定し、看護師へ別途共有する。看護師は QR を読み取った後、毎回コードを入力して送信する。

追加の決定(2026-11-03、ユーザー。改訂2):
6. **実機検証**はまず Galaxy S24 Ultra(Android)で行う。iPhone は協力者の端末で追加確認し、本格運用の前に両方を検証する。
7. **IAM の権限付与は原則承認**。ただし付与先・付与対象・必要な権限を事前に明示し、最小権限の方法を優先する(§8-5)。実際の変更は別途確認してから行う。
8. **アクセスコードは設定後に再表示しない**。設定画面には「設定済み」と表示し、管理者・副管理者は新しいコードに変更できる(§4・§8-1)。
9. あわせて、ブラウザからのアップロードに必要な **CORS**、**ファイルサイズの制限**、**送信途中の失敗・再送時の重複防止**を技術設計で確認する(§8-2)。

## 1. 目的と前提

- 白内障手術後、手術室(3階)の眼科カートに掲示した IOL シールの台紙を、医師が外来へ運ばなくてよくする。手術室の看護師が台紙を個人のスマートフォンで撮影して送り、医療機関と、施設が許可したディーラーが閲覧する。
- 台紙には患者氏名・ID などの個人情報はない(撮影時にも写し込まない。§3 の ⓘ と QR シールの注意書きで徹底する)。
- 画質の優先: 手書きの大きな「×」と、シールの小さな文字(型番・度数・シリアル)が拡大して読めること。
- 看護師の操作は最小限。Google ログインは不要で、施設専用の QR コード(入口)と、別途共有されたアクセスコード(数字6桁以上)で送信を許可する。
- 写真は原則としてスマートフォンの写真ライブラリに残さない。
- 画面は既存の IOL Order と同じ見た目(白背景・カード・補助ボタン 36px・ⓘ・説明文の常時表示なし)。

## 2. 全体像

```
既存の台紙(使い方は従来どおり)       看護師のスマホ(sticker.html)              保存(施設ごと・サーバー専用)        閲覧
┌────────────────────┐  QR 読取  ┌───────────────────────┐  送信  ┌────────────────────┐  ┌─ 医療機関: 注文画面のメニュー「IOLシール写真」
│ シールを貼る / ×を書く  │ ───────▶│ ①コード入力(毎回)          │ ─────▶│ Storage: 画像          │─▶│   施設の所属者全員
│ [QRシール]を貼り足すだけ │         │ ②撮影 → ③確認 → ④完了     │        │ Firestore: 送信日時など │  └─ ディーラー: dealer.html のメニュー「シール写真」
└────────────────────┘         └───────────────────────┘        └────────────────────┘      施設が共有を許可した会社の担当者だけ
```

- 入口は `sticker.html`(`dealer.html` と同じく注文画面とは別の入口。ヘッダーは共通の見た目で、見出しは「IOLシール写真」、施設名はコードの確認後にだけ出す)。
- QR の中身は `https://iol.medconf.jp/sticker.html#f=<施設の入口トークン>` だけ。施設 ID もアクセスコードも含めない(トークンは施設設定で発行する不透明な値。§8-1)。
- 1枚の写真 = 1件の記録。台紙1枚を2〜3枚に分けて撮ってもよい(「続けて撮影」。同じコードの確認の中では再入力しない)。

## 3. 看護師用(sticker.html。スマートフォン専用の見た目。PC でも動く)

### 3-1. 操作フロー

```
QR 読取 ─▶ [コード入力](毎回) ─▶ [撮影](開くとすぐカメラ) ─▶ シャッター ─▶ [確認](ピンぼけの疑いがあれば警告) ─▶ 送信 ─▶ [完了] ─▶ 続けて撮影 / 終了
```

- コードの確認は、その画面を開いている間(ブラウザのタブのメモリ。最長 30 分)だけ有効。タブを閉じる・「終了」を押す・30分経つと、次は再入力。端末には何も保存しない。
- 撮影した写真は、送信が終わるまで画面のメモリにだけ置く。端末への保存・共有・ダウンロードの操作は置かない。

### 3-2. ① コード入力

```
┌──────────────────────────┐
│ IOLシール写真                     │  ← 共通のヘッダー(施設名はまだ出さない)
├──────────────────────────┤
│  アクセスコード                 ⓘ │
│  ┌────────────────────┐   │
│  │ ● ● ● ● ● ●           │   │  ← 半角数字(inputmode=numeric、autocomplete=one-time-code は使わない)。6桁以上
│  └────────────────────┘   │
│  [        次へ        ](主要ボタン)  │
│  コードが違います(必要なときだけ赤字)  │
└──────────────────────────┘
```

- ⓘ: 「施設から共有されたアクセスコードを入力してください。コードは施設の管理者・副管理者が設定・変更します。患者情報が写らないように撮影してください。」
- 連続して間違えたときは一定時間受け付けない(「しばらくしてからお試しください」。回数・残り時間は表示しない)。
- QR なしで `sticker.html` を開いた(トークンがない・無効な)場合は「台紙のQRコードを読み取って開いてください」とだけ表示する(施設名は出さない)。
- 確認が通ると、ヘッダーの下に施設名を出し(送り先の確認)、② へ。

### 3-3. ② 撮影

```
┌──────────────────────────┐
│ ○○眼科                      ⓘ │
├──────────────────────────┤
│ ┌──────────────────────┐ │
│ │     カメラ映像(縦いっぱい)     │ │  ← 四隅に薄いガイド(台紙を枠に収める目安)
│ └──────────────────────┘ │
│            ( ◯ ) 大きなシャッター   │
│  [ライトを点ける](対応端末だけ・補助)  │
└──────────────────────────┘
```

- 開いたらすぐ背面カメラを起動(`getUserMedia`。最大の解像度を要求し、端末の上限で撮る)。写真ライブラリを経由しないので端末に残らない。
- カメラを使えない端末・許可されなかったときは「カメラを起動できません」+ [カメラで撮影](ファイル選択 `capture="environment"`)に切り替える(この経路は端末により写真が残ることがあるため、ⓘ にその旨を書く)。
- ⓘ: 「台紙全体が枠に入るように、真上から撮ってください。文字が読めるよう明るい場所で。患者情報が写らないようにしてください。」

### 3-4. ③ 確認

```
┌──────────────────────────┐
│ ┌──────────────────────┐ │
│ │   撮影した画像(ピンチで拡大)   │ │
│ └──────────────────────┘ │
│ ⚠ ピンぼけの疑いがあります。文字が   │  ← 判定したときだけ(黄色の注意)
│   読めるか拡大して確認してください  │
│  [ 撮り直す ]      [   送信   ]     │  ← 送信は主要ボタン。警告があっても送れる
└──────────────────────────┘
```

- ピンぼけの判定: 画像を縮小してグレースケールにし、ラプラシアンの分散で鮮鋭度を測る(しきい値は実機で調整。判定の結果は記録に残す)。
- 送る画像: **撮影した解像度のまま JPEG**(品質・長辺の上限は保留。§0-3。実機で文字の判読と容量を見て決める。第1段階の暫定は「縮小なし・JPEG 品質 0.92」)。送信前に画面上で容量を見せる必要はない。
- 送信中は [送信] を「送信中…」にして二重送信を防ぐ。失敗したら画像は残したまま「送信できませんでした。通信状態を確認して、もう一度お試しください」+ [再送信]。

### 3-5. ④ 完了

```
┌──────────────────────────┐
│          ✓ 送信しました            │
│       11/4(火) 10:32  1枚目        │  ← この確認の中で送った枚数
│  [   続けて撮影   ](主要ボタン)     │
│  [ 終了 ](補助)                    │
└──────────────────────────┘
```

- 「続けて撮影」で ②(カメラは起動したまま。コードの再入力なし)。「終了」で入口の案内に戻し、コードの確認と画像を画面のメモリから消す。
- 送信済みの写真の一覧・削除は看護師の画面には置かない。誤送信は医療機関側で削除する(§5)。

## 4. 施設設定「IOLシール写真」(施設管理者・副管理者)

既存の施設設定の1セクション(「ディーラー画面での閲覧」の次。折りたたみ・ⓘ・自動保存の流儀は他のセクションと同じ)。

```
IOLシール写真 ▲ ⓘ
  アクセスコード   設定済み(2026/11/03 変更)  [変更]   ← 未設定なら「未設定」+[設定]。コードは再表示しない。変更: 半角数字6桁以上を入力 / [自動で作る]。[変更する](確認ダイアログ。変更後はその画面に1回だけ新しいコードを表示し、看護師へ共有する案内)
  QRコード        [QRコードを表示・印刷]        ← 別画面(§4-1)。QR だけ。コードは載せない
  ディーラーへの共有  (「ディーラー画面での閲覧」の各発注先に ☐ IOLシール写真も共有する。§6)
```

- アクセスコードの変更はすぐ有効(以後の確認は新しいコード)。設定後は「設定済み」と変更日だけを表示し、コードは再表示しない(忘れたら変更する)。ⓘ: 「コードは台紙やQRコードには載らず、設定後に再表示もできません。看護師へは別途お伝えください。忘れた場合は新しいコードに変更してください。」
- 「送信の受け付け」の一時停止・保存期間は第2段階。

### 4-1. QR コードの表示・印刷(A4。`@media print` は R07 の帳票と同じ方式)

```
○○眼科  IOLシール写真                                  (右上に印刷日)
┌───────┐  使用したシールの台紙を撮影して送るためのQRコードです。
│  [QR]   │  1. スマートフォンのカメラで読み取る  2. アクセスコードを入力  3. 台紙を撮影して送信
└───────┘  患者氏名・IDは書かない・写さない
(同じ QR を 4×2 = 8 枚、切り取り線付きで並べる。既存の台紙・カートに貼る用)
```

- 載せるのは QR・施設名・3行の手順・注意書きだけ。URL の文字列・アクセスコードは載せない。
- 既存の台紙はそのまま使い、QR のシール(または小さな紙)を貼り足す。台紙の様式変更は不要。

| 段階 | 内容 |

## 8. 技術設計(認証・画像の保存・閲覧の権限)

Functions・Rules・Storage はいずれも新規の領域に閉じ、注文の受付・メール・ディーラー受注一覧の処理には組み込まない。既存の機能スイッチとは別に `STICKER_PHOTO_ENABLED`(既定 false)と、第1段階で有効にする施設の一覧 `STICKER_PHOTO_FACILITY_IDS` を設ける。

### 8-1. 入口トークンとアクセスコード(看護師の送信の認可)

- **入口トークン**(QR の `#f=`): 施設設定で初めて QR を表示するときにサーバーが発行する 128 ビットの乱数(URL 安全な文字列)。`stickerEntries/{token}` → `{ facilityId, status: active|revoked, createdAt }` に保存し、施設の文書には `stickerEntryToken` として参照を持つ。施設が「QR を作り直す」と旧トークンは `revoked`(印刷済みの古い QR を無効にできる)。トークンだけでは何もできない(コードが必須)。
- **アクセスコード**: 半角数字6桁以上、上限 12 桁。`facilities/{fid}/stickerSettings/access` にハッシュ(bcrypt 相当。コードが短いため salt + 高いコスト)と `updatedAt`・`updatedBy` を保存。平文は保存しない(決定 §0-8: 設定後は「設定済み」と変更日だけを返し、再表示の API は作らない。忘れたら変更する運用)。Rules: `stickerSettings` はクライアントから読み書きとも拒否し、設定の変更も Functions 経由にする(コードのハッシュ化をサーバーで行うため)。
- **確認の流れ**(callable `stickerPhotoApi`、ログインなし = `auth` なしを許可する唯一の関数。App Check は導入後に必須にする):
  1. `verify { token, code }` → トークンが active・コードのハッシュが一致なら、**送信チケット**(サーバー署名の HMAC トークン。中身: 施設 ID・発行時刻・有効期限 30 分・乱数)と施設名を返す。チケットはタブのメモリにだけ置く。
  2. 失敗はトークンの有無・コードの違いを区別しない同じ応答。**回数制限**: トークンごとに 10 回/10 分、送信元 IP ごとに 30 回/10 分(`rateLimits` と同じ仕組み)、超えたら 15 分停止。6桁の総当たり(100万通り)はこの制限で実用上不可能。コードを変えると、旧コードでの確認は以後失敗する(チケットの有効期限内の送信は、チケットに「コードの世代」を含めて拒否する)。
- 監査: `verify` の成功・停止、`complete`、削除を `stickerAuditLogs` に記録(IP は保存せずハッシュのみ)。

### 8-2. 画像の保存(Firebase Storage を新規に使う)

- バケットは既定の `medconf-iol-dev.appspot.com`(別のプロジェクトは作らない)。パス `stickerPhotos/{facilityId}/{yyyy}/{mm}/{photoId}.jpg`。サムネイル(長辺 400px)は `…/{photoId}_thumb.jpg` に Functions が作る(一覧の読み込みを軽くする。原本は触らない)。
- バケットは写真専用に新設する(`medconf-iol-dev-sticker-photos`。同じプロジェクト内。既定のバケットと分けることで、権限の付与・CORS・保存期間の設定を写真だけに限定できる)。**Storage Rules は全面拒否**(クライアントからの読み書きなし)。
- **送受信の経路(2案。§8-5 の権限と対)**。最小権限を優先し、**A 案を推奨**する。
  - **A 案(推奨): Functions がプロキシ**。アップロードは HTTP 関数 `stickerPhotoUpload`(onRequest)に、ブラウザが画像のバイト列をそのまま PUT する(ヘッダーにチケット・アップロードキー・SHA-256)。関数が検証してから自分の資格情報で Storage に書く。閲覧も HTTP 関数 `stickerPhotoImage`(onRequest)が、所属・許可を確認してから Storage から読み出して返す(短時間のキャッシュ可、`Cache-Control: private`)。**署名付き URL を使わないので `iam.serviceAccountTokenCreator` は不要**。必要なのはバケットへのオブジェクトの読み書き・削除だけ。関数の帯域と実行時間を使うが、量(§8-2 末尾)からみて問題ない。HTTP 関数のリクエスト本文の上限は 32MB。
  - **B 案: 署名付き URL(V4)**。callable が PUT 用・GET 用の短時間の URL を返し、ブラウザがバケットと直接やり取りする。関数の負荷は小さいが、実行サービスアカウントに自分自身への `iam.serviceAccountTokenCreator`(署名)が必要で、バケットに CORS の設定が要る。
- **CORS**: A 案では HTTP 関数が応答する(`Access-Control-Allow-Origin: https://iol.medconf.jp` のみ。`OPTIONS` の事前要求に `PUT, GET`・`Content-Type, X-Sticker-Ticket, X-Upload-Key, X-Content-Sha256`・`Access-Control-Max-Age: 3600` を返す。ほかのオリジンは拒否)。バケット側の CORS 設定は不要。B 案ではバケットに `[{ origin: ["https://iol.medconf.jp"], method: ["PUT","GET"], responseHeader: ["Content-Type"], maxAgeSeconds: 3600 }]` を設定する(`gsutil cors set`。運営者の操作)。ローカルの検証はエミュレータ(オリジン `http://127.0.0.1:*` を許可するのはエミュレータの設定だけ)。
- **ファイルサイズの制限**(多段):
  1. ブラウザ: 送信前に JPEG の大きさを確認。**20MB** を超えるときは送らず「画像が大きすぎます。もう一度撮影してください」(実機検証で撮影した解像度のままの容量を見て、上限と必要なら縮小の条件を §0-3 で決める。Galaxy S24 Ultra の 12MP 既定で 3〜6MB、高解像度モードではこれを超えうる)。
  2. HTTP 関数: `Content-Length` が **15MB**(第1段階の暫定。検証後に見直す)を超える・ない場合は本文を読まずに 413 で拒否。先頭のバイト列が JPEG(`FF D8 FF`)でなければ 415。実際に受け取ったバイト数が宣言と違えば破棄。
  3. 件数: 1チケット(30分)あたり 30 枚、施設あたり 1 日 200 枚、1 日 1GB。超えたら 429 で「本日の送信の上限に達しました」。
  4. バケット: オブジェクトのライフサイクルは第3段階(保存期間)まで設定しない。
- **送信途中の失敗・再送時の重複防止**(アップロードキーで冪等にする):
  1. ブラウザは **撮影した写真ごとに1回だけ** アップロードキー(UUID)を作り、その写真の再送ではずっと同じキーを使う(「撮り直す」で新しい写真になったら新しいキー)。あわせて画像の SHA-256 を計算して送る。
  2. サーバーは `(施設, チケット, アップロードキー)` → `photoId` を決定的に決める(ハッシュ)。Storage のオブジェクト名は `photoId` なので、再送は同じオブジェクトへの上書き(PUT は冪等)。登録(Firestore の文書 ID も `photoId`)はトランザクションで「なければ作る」。同じキーの2回目以降は **既存の記録を返して 200**(重複を作らない)。
  3. 同じチケット内で、キーが違っても **同じ SHA-256** の画像が来たら(ブラウザのやり直しでキーを失った場合など)、新しい記録を作らずに既存の `photoId` を返す(24 時間・同じ施設の範囲で照合)。
  4. 本文の受信が途中で切れたとき(`Content-Length` に満たない)は保存せず 400。ブラウザは自動で最大 3 回(1・2・4 秒後)再送し、それでも失敗したら [再送信] を出す(画像は画面のメモリに残す)。
  5. 保存に成功したのに応答がブラウザに届かなかった場合も、再送が同じキーで同じ結果を返すので二重にならない。「送信しました」の枚数は、サーバーの応答の `created: true/false` で数える(重複は数えない)。
  6. 受信して保存したがサムネイルの作成に失敗した場合は、記録を残したまま再試行(サムネイルがなければ一覧は原本を縮小して出す)。孤立したオブジェクト(記録のないもの)は 1 日後に削除するスケジュール関数で片付ける。
- **メタデータ** `facilities/{fid}/stickerPhotos/{photoId}`: `{ facilityId, takenAt(サーバー時刻), width, height, bytes, blurWarned: bool, ticketId(どの確認でまとめて送られたか), storagePath, thumbPath, deleted?: { at, by }, createdAt }`。患者情報・端末の識別子は持たない。Rules: 施設の所属者は読める(`isMember(fid)`。一覧の問い合わせは `facilityId` で絞ったものだけ)、書き込みはすべて拒否(Functions だけ)。
- **画像の読み出し**(A 案): 一覧は `list`(callable。最大 60 件/回)でメタデータを受け取り、サムネイル・原本は `stickerPhotoImage?photo=…&size=thumb|full`(HTTP 関数。Firebase Auth の ID トークンをヘッダーで送り、所属または共有の許可を確認)から `<img>` で読む。URL をページの外へ持ち出さない(ダウンロード・共有ボタンは置かない)。B 案なら短時間の署名付き URL。
- **削除**(医療機関の管理者・副管理者): `delete { photoId }` → Firestore に削除の記録を残し、Storage の原本とサムネイルを削除する(復元なし。誤送信用)。
- 容量と料金の目安: 1枚 3〜8MB(縮小なしの場合)× 1 日 5 枚 × 20 営業日 ≈ 0.3〜0.8GB/月/施設。保存期間を決めるまでは残す(第3段階で自動削除)。

### 8-3. 閲覧の権限

| 誰 | できること | 判定 |
| --- | --- | --- |
| 看護師(ログインなし) | 送信だけ(自分が送った写真の一覧・削除もできない) | 入口トークン + アクセスコード → 送信チケット(§8-1) |
| 医療機関の所属者(4 役割) | 自施設の写真の一覧・拡大 | Rules `isMember(fid)`(メタデータ)+ 画像は `stickerPhotoImage` が所属を再確認して返す(A 案。B 案なら署名付き URL) |
| 医療機関の管理者・副管理者 | 上に加えて、アクセスコードの設定・QR の表示と印刷・ディーラーへの共有の許可と取消・写真の削除 | `isFacilityManager(fid)`(サーバーで再確認) |
| ディーラーの担当者 | 共有を許可した施設の写真の一覧・拡大(削除不可) | 会社の担当者として有効(既存の `dealerPortalApi` と同じ確認)× 施設の **写真の共有の許可**が有効 × 許可の後に送られた写真 |
| 運営者(platformAdmin) | 停止・復旧の運用操作のみ(写真の閲覧は施設の所属者と同じ条件に限る) | 既存の運営者の確認 |

- **ディーラーへの共有の許可**: 受注一覧の閲覧の許可(`dealerPortalGrants`)とは**別の許可**として `dealerPortalGrants` に `kind: "stickerPhotos"` の文書を作る(同じ会社・同じ発注先の関連付け `dealerPortalLinks` に対して、受注の許可と写真の許可を独立に持つ)。施設設定「ディーラー画面での閲覧」の各発注先に「IOLシール写真も共有する」のチェックを置き、ON で許可(`effectiveFrom`)、OFF で取消。受注一覧の許可がなくても写真だけ共有できる(逆も可)。許可した時点の発注先の指紋の照合も既存と同じ。
- ディーラー側の一覧は `dealerPortalApi` ではなく `stickerPhotoApi` の `dealerList` と、同じ `stickerPhotoImage`(ディーラーの担当者の確認を含む)で返す(受注一覧の処理に組み込まない方針)。返すのは写真のメタデータと画像だけ(施設名は許可の範囲の表示用)。
- 許可より前に送られた写真は返さない(`takenAt >= effectiveFrom`)。取消の後は一覧から消え、画像も読めなくなる(A 案は毎回確認。B 案は署名付き URL の残り時間だけ見える)。

### 8-5. IAM の権限(付与先・付与対象・必要な権限。変更は別途確認の後に行う)

現状(2026-11-01 の調査、`docs/dealer-portal.md`): 本番の Functions の実行サービスアカウント(`RUNTIME_SERVICE_ACCOUNT`。プロジェクト内の専用アカウント)のプロジェクトの役割は `roles/datastore.user`・`roles/eventarc.eventReceiver`・`roles/logging.logWriter` だけで、Storage への権限はない。

| 案 | 付与先 | 付与対象(スコープ) | 役割 | 用途 |
| --- | --- | --- | --- | --- |
| **A(推奨)** | 実行サービスアカウント(`RUNTIME_SERVICE_ACCOUNT`) | **写真専用バケット** `medconf-iol-dev-sticker-photos` だけ(バケット単位の IAM。プロジェクト単位にはしない) | `roles/storage.objectAdmin`(オブジェクトの作成・読み取り・削除。削除は誤送信の削除と孤立ファイルの片付けに要る) | プロキシ経由の保存・読み出し・削除 |
| B | 同上 | 同上 + 同じ実行サービスアカウント **自身**(サービスアカウント単位の IAM。プロジェクト単位にはしない) | 上に加えて `roles/iam.serviceAccountTokenCreator`(自分自身への署名。鍵は作らない) | 署名付き URL の発行 |

- どちらの案でもサービスアカウントの鍵は作らない(Application Default Credentials で署名・アクセス)。付与は Firebase のプロジェクト `medconf-iol-dev` の中だけ。
- A 案なら追加する役割はバケット1つへの `storage.objectAdmin` だけで済む(最小)。B 案は署名のための役割が増える。**A 案を採用する前提で進め、実機検証で関数経由の送信時間に問題があれば B 案を再検討する。**
- 付与の手順(承認後): バケットの作成(リージョン `asia-northeast1`、均一なアクセス制御、公開アクセスの防止)→ バケットの IAM に上記の役割を付与 → Storage Rules を全拒否で配備 → Functions を配備 → 読み取りだけの確認スクリプトで、実行サービスアカウント以外(クライアント・匿名)から読めないことを確かめる。
- スケジュール関数(孤立ファイルの削除・将来の保存期間)は同じ実行サービスアカウントで動かす(Cloud Scheduler の呼び出しの権限は Firebase が構成する範囲)。

### 8-4. テスト・運用

- unit: ピンぼけ判定(鮮鋭な画像/ぼけた画像の合成データ)、コードの形式(半角数字 6〜12 桁)、チケットの期限と世代、QR の URL の組み立て。
- Rules: `stickerSettings`・`stickerEntries`・監査ログはクライアント全拒否、`stickerPhotos` は所属者だけ読める・書けない、Storage Rules は全拒否。
- Functions(エミュレータ): `verify` の成功・失敗・回数制限・コード変更後の拒否、`requestUpload`/`complete` の上限と整合、`list`/`imageUrl` の権限(所属者・他施設・未ログイン)、`dealerList` の許可の有無と `effectiveFrom`、削除の権限と記録。
- ブラウザ(Playwright の仮想カメラ): 看護師の4画面(コードの誤り・撮影・警告・送信・続けて撮影・終了でメモリから消える)、施設設定(コードの変更・QR の印刷画面にコードがないこと)、医療機関とディーラーの一覧・拡大・削除の可否、スマホ/PC。
- 実機検証(着手前。§0-6): Galaxy S24 Ultra で、`getUserMedia` の解像度(要求 4096×3072 に対して実際の値)、撮影した解像度のままの JPEG の容量、関数経由の送信時間(院内 Wi-Fi と 4G/5G)、シールの文字・シリアルの判読(拡大表示)、ファイル選択の経路で写真が端末に残るか。結果で §0-3 の圧縮条件・§8-2 のサイズ上限を確定する。iPhone は協力者の端末で同じ項目を確認し、本格運用の前に両方を済ませる。
- 配備の順: 写真専用バケットの作成と IAM(§8-5。承認後)→ Storage Rules(全拒否)→ Firestore Rules → Functions(`stickerPhotoApi`・`stickerPhotoUpload`・`stickerPhotoImage`・サムネイル・孤立ファイルの削除)→ 画面(`sticker.html` は `stamp-assets` の対象に追加)。機能スイッチは最初は許可した施設だけ。
- マニュアル: 医療機関用 2(一覧の見方)・3(施設設定: コード・QR・共有)、ディーラー用 02(シール写真)。看護師向けの操作は QR シールの3行の手順と画面の ⓘ で足りる想定(必要なら 1 に短い節)。
